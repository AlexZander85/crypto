# Спецификация интерактивного модуля «Песочница Freqtrade»

Версия 1.0 · для реализации ИИ-агентом · язык интерфейса — русский

## 0. Как читать этот документ

- **ДОЛЖЕН / MUST** — обязательное требование, без него модуль не принимается.
- **СЛЕДУЕТ / SHOULD** — ожидается в v1, допустимо перенести в v1.1 при явном согласовании.
- **МОЖЕТ / MAY** — необязательная возможность.
- Все числа, названия и пороги, помеченные ⚑, взяты из текстов уроков FT-01…FT-20, 4.4, 4.5, 5.1, 5.5, 5.6, П1, П5 и **не подлежат изменению без правки уроков** — иначе песочница разойдётся с курсом.
- Идентификаторы станций — `SB-1…SB-5`, правил линтера — `CFG-xxx`, событий dry-run — `EV-xxx`, артефактов — `ART-xxx`. Агент ДОЛЖЕН сохранить эти ID в коде (константы, `data-testid`), чтобы уроки могли ссылаться на них.

## 1. Назначение

### 1.1. Проблема
Freqtrade Academy — 27 уроков без единого интерактива, при этом это модуль, где ученик впервые делает что-то «по-настоящему»: собирает конфиг, читает 40-строчный английский отчёт, наблюдает бота 8 недель. Всё это он делает один на один с терминалом, и именно здесь новички бросают курс.

### 1.2. Что такое песочница
Единый интерактивный модуль в браузере, который **воспроизводит полный цикл работы с Freqtrade без установки Freqtrade**: конфигурация → данные и бэктест → чтение отчёта → сухой прогон → сверка и допуск. Внутри — детерминированный учебный движок, имитирующий поведение Freqtrade с точностью, достаточной для обучения (см. §6.7 «Заявленные упрощения»).

### 1.3. Учебные результаты
После прохождения ученик ДОЛЖЕН уметь:
1. Прочитать `config.json` и назвать назначение каждого ключа из учебного набора; найти опасную ошибку (реальные деньги вместо песочницы, риск выше устава).
2. Посчитать размер ставки от риска ⚑ (`stake × |stoploss| ≤ 1–2 % депозита`).
3. Прочитать отчёт бэктеста **в правильном порядке** ⚑: сделки → просадка → риск-метрики → прибыль → разбивки.
4. Найти подсматривание в будущее по симптомам (слишком ровная кривая, Шарп > 5) и по коду (`shift(-1)`, `center=True`, слияние информативных пар без сдвига, `bfill`).
5. Провести 8-недельную dry-run кампанию, не вмешиваясь «по голове», и вести журнал вмешательств ⚑ («мир или голова»).
6. Посчитать Execution Deviation ⚑ и принять решение по коридорам (< 10 % / 10–25 % / > 25 %).
7. Заполнить чек-лист допуска 20/20 ⚑ и честно отложить микро-лайв, если пункт не закрыт.

### 1.4. Чем модуль НЕ является
- Не исполняет настоящий Freqtrade и произвольный Python (v1 — см. решение §6.2).
- Не ходит в интернет и не подключается к биржам; все данные вшиты.
- Не даёт «прибыльную стратегию»; учебные стратегии сконструированы умеренными по результату.
- Не сравнивает учеников между собой по доходности (анти-паттерн, часть 3 аудита §3.4).

## 3. Педагогические принципы (обязательны для каждого экрана)

1. **Цель одной фразой** над каждым экраном: не «поиграй с конфигом», а «Найди галочку, которая отделяет песочницу от реальных денег».
2. **Задание, а не свободная игра.** Свободный режим — отдельно.
3. **Момент «ага»** задан явно и подсвечивается при достижении (например: ученик снял галочку `dry_run` — экран краснеет и появляется плашка «Сейчас бы ушёл настоящий ордер»).
4. **Дефолты = числа из текста уроков** ⚑ (`dry_run_wallet 1000`, `max_open_trades 3`, `stoploss -0.10`, `ROI {0: 0.06, 240: 0.02}`, EMA16/EMA200, RSI14, порог 35, комиссия 0.1 %, 8 недель dry-run).
5. **Возможность проиграть.** Dry-run можно провалить (вмешательства «по голове», пропущенный сбой). Без проигрыша нет эмоции.
6. **Артефакт на выходе** каждой станции, который сохраняется в профиль и предъявляется на следующей.
7. **Русский интерфейс без исключений.** Английский остаётся только там, где он есть в настоящем Freqtrade (ключи `config.json`, заголовки отчёта, команды CLI) — и каждый такой токен ДОЛЖЕН иметь русскую подсказку при наведении и перевод по кнопке «Перевести» (§8.1).
8. **Обращение на «ты»**, единый герой Алексей и его учебный счёт 1000 USDT.

```
│           │ и данные  │ бэктеста  │ прогон    │ допуск      │
├───────────┴───────────┴───────────┴───────────┴─────────────┤

│  • Глоссарий (термины Freqtrade)                            │
│  • Подсказки (3 уровня, §8.2)                               │
└─────────────────────────────────────────────────────────────┘
```

### 4.2. Поток данных между станциями

```
SB-1  config ──┐
SB-2  strategy + params + dataset ──┤
                                    ├─► Движок бэктеста ─► BacktestResult ─► SB-3
                                    │
                                    └─► Движок dry-run (holdout + события) ─► DryRunSession ─► SB-4
                                                                                   │
                     BacktestResult(holdout-окно) + DryRunSession ─► Сверка ─► DeviationReport ─► SB-5
                                                                                   │
                     Журнал вмешательств + артефакты + ручные пункты ─► Чек-лист 20/20 ─► Verdict
```

Ключевой инженерный принцип: **один и тот же код стратегии и один и тот же исполняющий движок** используются и в бэктесте, и в dry-run — различаются только адаптеры данных и модель исполнения (урок 1.6 ⚑ «код стратегии одинаков, меняются адаптеры»). Это ДОЛЖНО быть реализовано буквально: класс `ExecutionModel` с двумя реализациями `IdealizedBacktestExecution` и `NoisyDryRunExecution`.

### 4.3. Ворота между станциями (учебный маршрут)

| Переход | Условие открытия |
|---|---|
| SB-1 → SB-2 | ART-01: линтер без ошибок уровня `error`; риск на сделку в коридоре 1–2 % |
| SB-2 → SB-3 | Просветный тест пройден (сигналы на ожидаемых свечах); данные проверены |
| SB-3 → SB-4 | ART-02 + ART-03: прочитаны три отчёта, lookahead-анализ зелёный, ≥ 80 сделок в окне ⚑ |
| SB-4 → SB-5 | Кампания 8 недель завершена (любым исходом) |
| SB-5 → финал | Вердикт вынесен и записан (в том числе «продлить dry-run») |

Ворота МОГУТ быть отключены флагом `?gates=0` (для преподавателя и свободного режима).

### 6.2. Стратегии: решение по исполнению кода

**Решение v1:** стратегии — **параметризованные шаблоны**, а не произвольный Python. Ученик видит настоящий Python-код шаблона (только чтение, с подсветкой и русскими комментариями к каждой строке), а параметры меняет формой. Логика шаблона реализована в JS/TS движке зеркально коду на экране.

Обоснование: исполнение Python в браузере (Pyodide + pandas + TA-Lib) — 30+ МБ, 10–20 с загрузки, недоступно на слабых устройствах и телефонах; для новичка задача «прочитать и понять» важнее «написать». Свободный код появится у ученика в настоящем Freqtrade (FT-05), куда песочница его и ведёт.

**MAY (v2):** режим «Свой код» на Pyodide для Свободной лаборатории.

Библиотека шаблонов v1:

| ID | Название на экране | Логика | Роль |
|---|---|---|---|
| `TutorialEmaRsi` | «Учебная: EMA + RSI» | EMA16 > EMA200, RSI14 пересекает 35 сверху вниз, volume > 0; выход — EMA16 < EMA200 ⚑ | базовая, FT-05 |
| `DipBuyerBTCFilter` | «Покупка отката с фильтром по BTC» | то же + BTC 1d: close > EMA50 (информативная пара со сдвигом) ⚑ | основная для FT-09…FT-20 |
| `NoisyScalper` | «Шумный скальпер» (антипример) | пересечение EMA3/EMA7 на 1h, 250+ сделок | демонстрация арифметики издержек (FT-13 ⚑: +100 % брутто → +25 % нетто) |
| `PerfectLiar` | «Идеальная (с утечкой)» | `DipBuyerBTCFilter` + скрытый дефект (§6.6) | Lookahead-детектив; в списке помечена только в свободном режиме |

Изменяемые параметры и их диапазоны: `rsi_buy ∈ [25, 40]`, `ema_fast ∈ [10, 30]`, `ema_slow ∈ [100, 250]`, `stoploss ∈ [-0.20, -0.03]`, `minimal_roi` (2 строки), трейлинг (3 параметра), `protections` (StoplossGuard ⚑ 24/3/12, MaxDrawdown, CooldownPeriod), `startup_candle_count` (задаётся учеником; проверяется в SB-2).

### 6.3. Движок бэктеста

Детерминированный, на TypeScript, без внешних зависимостей тяжелее 50 КБ. Алгоритм ДОЛЖЕН соответствовать описанию FT-06/FT-09/FT-10 ⚑.

```
для каждой пары:
  df = свечи; посчитать индикаторы (EMA, RSI, информативные — с корректным сдвигом);
  enter[t], exit[t] по правилам шаблона (только данные ≤ t)

state: balance = dry_run_wallet; open = []; closed = []; protectionsState
для t от startup_candle_count до N-1 (по всем парам синхронно по времени):
  # A. Выходы по открытым сделкам на свече t (пессимистичный порядок ⚑ FT-09):
  1) стоп: если low[t] ≤ stopPrice → выход по max(stopPrice, ?) …
       если open[t] < stopPrice (гэп) → выход по open[t]  ← «стоп проскочил глубже»
  2) ROI: цель по таблице minimal_roi для текущей длительности; если high[t] ≥ roiPrice → выход по roiPrice
       если и стоп, и ROI достижимы в одной свече → считаем стоп (пессимизм)
  3) трейлинг: пересчёт стопа после достижения offset
  4) exit-сигнал со свечи t-1 → выход по open[t]
  # B. Входы:
  если enter[t-1] == 1 и нет открытой сделки по паре и есть свободный слот (max_open_trades)
     и protections не блокируют и баланса хватает:
        market → цена open[t]
        limit  → цена по entry_pricing (open[t]*(1−offset)); исполняется, если low[t..t+timeoutCandles] ≤ лимит;
                 иначе отмена (reason = "timeout") — считается в статистике «пропущено по таймауту»
  комиссия fee на вход и на выход; PnL % = (exit/entry − 1) − 2·fee
  # C. protections обновляются по closed[]
```

Метрики результата (`BacktestResult`) — ДОЛЖНЫ включать всё, что читается в SB-3:
`trades, winRate, profitFactor, expectancy, totalProfitPct, absProfit, cagr, sharpe, sortino, calmar` (по дневной кривой), `maxDrawdownAbs, maxDrawdownRel, ddStart, ddEnd, avgDuration, exitReasons {roi, stoploss, trailing, exit_signal, force}, perPair[], perMonth[], leftOpenTrades, bestMonthShare, missedByTimeout, missedBySlot, fee, buyHold[]` (бенчмарк по каждой паре за то же окно ⚑ FT-09/1.11), `equityCurve[]`, `tradesList[]` (для экспорта и сверки).

Пороговые оценки для подсказок в SB-3 ⚑ (таблица FT-09): сделок < 30 — тревога; PF < 1.1 — тревога, > 2.5 на in-sample — подозрение на подгонку; DD > 25 % — тревога; лучший месяц > 50 % прибыли — «одна удача».

### 6.4. Учебный lookahead-анализ

Имитация `freqtrade lookahead-analysis` ⚑ FT-11/FT-13: движок прогоняет стратегию на одном отрезке при разной глубине доступного «будущего» (полная история vs обрезка по 4 контрольным точкам) и сравнивает сигналы на пересечении. Если сигналы различаются — вердикт «красный» с указанием класса дефекта (движок знает, какой дефект инжектирован, но ученику показывает только симптом; класс раскрывается после того, как ученик выбрал ответ в детективе).

Также `recursive-analysis`: сравнение значений индикаторов при `startup_candle_count` 200 vs 600 ⚑ FT-12.

### 6.5. Движок dry-run

Работает на `holdout-1h-8w` **через тот же код стратегии**, но с `NoisyDryRunExecution`:

| Параметр модели | Значение по умолчанию | Откуда |
|---|---|---|
| Проскальзывание на сторону | BTC/ETH: 1–3 bps, SOL: 2–6 bps, synthetic ALT: 10–40 bps; лог-нормально по seed | 1.8 ⚑ |
| Вероятность исполнения лимитки | 1.0, если цена прошла уровень на ≥ 2 тика; 0.6, если коснулась ровно; иначе 0 → таймаут | FT-06 |
| Частичное исполнение | 8 % лимитных входов исполняются на 40–70 % объёма | FT-06 |
| Задержка сигнала | 0–1 свеча при инфраструктурных событиях | FT-10 |
| Расширение спреда | ×5–15 в событиях EV-06 | 3.6 ⚑ |
| Пропуск сигналов | в окнах EV-02/EV-03 | 4.2 |

Скорость: 1 симулированная неделя = 60 с реального времени (8 недель за 8 минут ⚑); кнопки «пауза», «шаг = 1 день», «×2». Ученик МОЖЕТ уйти и вернуться — состояние сохраняется по неделям.

| Команда | Уровень | Требование перед исполнением |
|---|---|---|
| `/status`, `/profit`, `/daily` | 0 | — (но считается «взгляд»; ночные взгляды учитываются в счётчике П5) |

Стоимость вмешательства считается разницей между кривой «руки прочь» (эталонная сессия без вмешательств на том же seed) и фактической кривой, атрибутированной к сделкам, затронутым вмешательством.

**Белый список ночных событий** ⚑ П5: перед стартом ученик обязан составить белый список из 2–3 пунктов (выбор из 8 вариантов + свой). Ночные уведомления (00:00–07:00 по симулированному времени) вне белого списка показываются приглушённо с пометкой «пришло ночью — прочитаешь утром»; если ученик их открывает ночью — счётчик «ночных взглядов» растёт, и в итогах это переводится в «ментальный капитал» (условные баллы, П12).

| ID | Дефект | Как проявляется в отчёте | Код-симптом на экране |

### 7.2. SB-2 «Стратегия и данные»

**Цель одной фразой:** «Три функции пишешь ты. Всё остальное уже написано. Убедись, что твои три функции не подсматривают в будущее».

### 7.3. SB-3 «Отчёт бэктеста: читай в правильном порядке»

**Цель одной фразой:** «Первая строка отчёта — реклама. Правда — в третьей таблице».

#### 7.3.1. Экран

1. **«Прочитай отчёт №1»** — честный отчёт `DipBuyerBTCFilter`, год 1. 5. **«Три периода»** — таблица устойчивости: год 1, год 2 (OOS), старый период; авто-заполнение из трёх прогонов; вывод пишет ученик (свободный текст, 1–3 строки).

### 7.4. SB-4 «Сухой прогон: 8 недель за 8 минут»

**Цель одной фразой:** «Допуск — не про доходность. Допуск — про то, как ты вёл себя восемь недель».

#### 7.4.1. Подготовка (обязательный экран перед стартом)
1. **Белый список ночных событий** ⚑ П5 — выбрать 2–3 из списка: нет связи с биржей > 15 мин; сработала аварийная кнопка; бот отправил приказ, которого не мог; цены не совпадают с биржей; минус за день > дневного лимита устава; «странный сигнал»; новость; минус в пределах плана. Правильный список — первые 4 (не подсказывается; оценивается в итогах).
2. **Регламент наблюдения** ⚑ FT-19: время ежедневного `/profit` (выбор часа), день недельного разбора. Симулятор будет отмечать нарушения регламента (взгляды вне окна).
3. **Письмо из будущего** (SHOULD, П7): 3 строки «почему через 8 недель кампания провалится» — сохраняются и показываются в итогах рядом с фактом.
4. Плашка: «Параметры стратегии заморожены. Изменение после финального бэктеста аннулирует допуск» ⚑ FT-20.

#### 7.4.2. Экран кампании
- **Лента времени**: 8 недель, текущая позиция, день/ночь (ночь затемняет экран).
- **Панель FreqUI (упрощённая)**: кривая баланса, открытые сделки, журнал сделок, лог (русские строки в формате Freqtrade: `2024-… - freqtrade.freqtradebot - INFO - …` с подсказками — мост к FT-00).
- **Панель Telegram**: чат с уведомлениями и полем команд (кнопки + ввод).
- **Кнопки управления временем**: ▶ ⏸ шаг-день ×2.
- **Счётчики в углу** (видны ученику): вмешательства (мир/голова), ночные взгляды, дни без нарушений регламента.

Уведомления о событиях типа «мир» ДОЛЖНЫ быть отличимы от «головы» только по содержанию, **не по оформлению** — иначе тренажёр не работает.

#### 7.4.3. Недельный разбор
В конце каждой симулированной недели — пауза и экран «Воскресный разбор» ⚑ FT-20: uptime, число сигналов vs ожидание бэктеста (± %), средняя цена входа vs сигнальная (bps), win rate, просадка недели, записи журнала; ученик ставит двойную отметку недели ⚑ П8: «результат ±» и «процесс чист да/нет» с комментарием. Красный флаг недели: расхождение числа сигналов с бэктестом > 30 % ⚑.

#### 7.4.4. Итоги кампании
- Две кривые: «руки прочь» и «твоя»; разложение разницы по вмешательствам (таблица: неделя, команда, мир/голова, оправдано/нет, стоимость в USDT).
- Ночные взгляды × условная цена (ментальный капитал).
- Проверка белого списка: «ты не включил „бот отправил приказ, которого не мог“ — и пропустил EV-08 на 7-й неделе».
- Письмо из будущего рядом с фактом.
- Автозаполнение пунктов чек-листа CL-08…CL-13 (инфраструктура/оператор).
- Кнопка «Экспорт сделок dry-run» → SB-5.

Кампания считается **проваленной по процессу** (не по деньгам), если: ≥ 1 неоправданное вмешательство уровня 2, или изменение параметров, или пропущено событие «мир» без реакции > 24 симулированных часов. Провал не блокирует SB-5 — в SB-5 он станет основанием вердикта «продлить dry-run».

#### 7.4.5. «Ага»
На 7-й неделе после EV-07 (6 убытков подряд) и EV-10 (−8 %) большинство нажмёт `/stopentry` или `/forceexit all`. На следующей симулированной неделе восстановление даёт +4–6 %; итоги показывают: «Выключил на дне. Это стоило X USDT — ровно тот сценарий из 5.5».

### 7.5. SB-5 «Сверка и допуск»

**Цель одной фразой:** «Разница между „обещал“ и „получилось“ измеряется, а не чувствуется».

#### 7.5.1. Экран сверки
Две таблицы сделок рядом: **бэктест на holdout-окне** (движок прогоняет `IdealizedBacktestExecution` на тех же 8 неделях — ученику это объясняется: «то, что обещал бэктест на этом же отрезке») и **dry-run**. Авто-сопоставление по паре + времени входа (±1 свеча); несопоставленные подсвечены: «сигнал был, сделки не было» (таймаут/сбой/слот) и «сделка есть, сигнала не было» (дубль EV-08). Ученик подтверждает или правит пары вручную (drag).

Расчёт:
```
ED = (PnL_dry − PnL_bt) / |PnL_bt| × 100 %      (при |PnL_bt| < 1 % — показывать абсолютную разницу и предупреждение)
дополнительно: Δчисло сделок %, среднее проскальзывание входа bps, средняя задержка исполнения (свечи),
               Δwin rate п.п., доля сделок, пропущенных по таймауту
```
Коридоры ⚑ 4.5: `|ED| < 10 %` — норма, допуск; `10–25 %` — серая зона, уточнять модель; `> 25 %` — стоп. Ученик выбирает действие; система сверяет с коридором и объясняет. Отдельно: если ED «слишком хороший» (dry-run лучше бэктеста > 10 %) — плашка «ищи утечку» ⚑ FT-16.

Команды-переводчик: `freqtrade backtesting … --export trades` и экспорт из FreqUI — с пояснением, как это делается в настоящем Freqtrade.

## 8. Сквозные системы

### 8.1. Словарь интерфейса Freqtrade → русский

Единый файл `glossary.ft.json`: `{ token, ru_short, ru_why, lesson, pronunciation? }`. Минимальный набор ДОЛЖЕН покрывать: все ключи учебного конфига; все заголовки отчёта (`Tot Profit`, `Avg Duration`, `Win Draw Loss Win%`, `Drawdown`, `Profit factor`, `Expectancy`, `Sortino`, `Sharpe`, `Calmar`, `Left open trades`, `Exit Reason`, `roi/stop_loss/exit_signal/trailing_stop_loss/force_exit`, `Best/Worst Pair`, `Market change`); команды (`backtesting, download-data, lookahead-analysis, recursive-analysis, hyperopt, trade, list-data, plot-dataframe, install-ui, show-config`); флаги (`-c, --strategy, --timerange, --timeframe, --export, --spaces, --epochs, --hyperopt-loss, --fee`); термины стратегии (`IStrategy, populate_indicators, populate_entry_trend, populate_exit_trend, enter_long, exit_long, minimal_roi, stoploss, startup_candle_count, informative_pairs, merge_informative_pair, protections, StoplossGuard, CooldownPeriod, MaxDrawdown, trailing_stop_*`); команды Telegram.

Правило: русский термин первым и постоянно в текстах песочницы; английский — там, где он реально печатается Freqtrade, с подсказкой. Пример подсказки: `Left open trades` → «Позиции, не закрытые к концу теста. Включены ли они в итог? Проверь — они могут держать бумажный плюс».

### 8.2. Подсказки трёх уровней
1. **Наведение** — одна строка «что это».
2. **«Почему так»** — 2–4 предложения из урока (без открытия урока).
3. **«Где в курсе»** — ссылка `lesson://FT-09#metrics` (глубокая ссылка на блок урока).

Учёт: `hintsUsed` в состоянии задания; влияет только на бейджи («Нашёл утечку до подсказки»), никогда — на доступ.

### 8.3. Терминал-переводчик
Панель в нижней части всех станций. Режим A (по умолчанию): каждое действие кнопкой показывает эквивалентную команду CLI с аннотацией по флагам. Режим B (SHOULD): ввод команды вручную; поддерживаемая грамматика — 8 команд из §8.1 с их флагами; ошибки — реальные строки Freqtrade (`freqtrade: error: unrecognized arguments: …`) с русским переводом снизу. Это мост к Py-15/FT-00.

### 8.4. Журнал
Две вкладки: **Эксперименты** (каждый бэктест: дата, стратегия, параметры, диапазон, fee, ключевые метрики, комментарий ученика — обязателен для «зафиксировать в журнал») и **Вмешательства** (§6.5). Экспорт в Markdown в формате, совпадающем с `journal/interventions.md` и `journal/weekly.md` из FT-20 ⚑ — чтобы ученик мог продолжить тот же файл в настоящем проекте.

- Числа — с неразрывным пробелом и русской типографикой (`1 000 USDT`, `−10 %`).
- Все тексты — в `locale/ru.json`; строки не хардкодятся в компонентах.

## 10. Технические требования

**Стек.** TypeScript; фреймворк — тот же, что у платформы курса (если платформа на React — React 18 + Zustand; иначе согласовать). Движки (`backtest`, `dryrun`, `linter`, `lookahead`) — чистые модули без DOM, запускаются в Web Worker. Графики — лёгкая библиотека (uPlot или аналог, ≤ 50 КБ). Сборка модуля ≤ 400 КБ gzip без данных; данные — ленивая загрузка по станциям (≈ 1.5 МБ gzip на все наборы).

**Детерминизм.** Единый PRNG (mulberry32/xoshiro) от `seed`; никаких `Math.random`. Тесты на воспроизводимость обязательны.

**Производительность.** Бэктест 30 мес × 3 пары ≤ 2 с; пересчёт линтера/карты риска ≤ 100 мс; dry-run тик (1 свеча) ≤ 5 мс.

**Хранение.** `localStorage` + опциональный API платформы; размер состояния ≤ 2 МБ (список сделок хранить компактно).

**Офлайн.** После первой загрузки станции работают без сети.

**Адаптивность.** Минимальная ширина 1024 px для SB-3/SB-5 (две таблицы); на телефоне — только SB-4 (уведомления и команды) в упрощённом виде (SHOULD).

**Доступность.** Клавиатурная навигация, aria-подписи, контраст ≥ 4.5:1, состояние «мир/голова» дублируется текстом (не только цветом).

**Тестирование.**
- Юнит-тесты движков с «золотыми» файлами: `golden/TutorialEmaRsi.trades.json`, `golden/dryrun.seed3141592.json`, `golden/linter.cases.json`.
- Скриншот-тест формата отчёта.
- Сценарные тесты (Playwright): проход маршрута «идеальный ученик» и «ученик, вмешавшийся на 7-й неделе».

**Телеметрия (события для платформы).** `sandbox.station.opened`, `sandbox.task.completed {taskId, attempts, hintsUsed}`, `sandbox.artifact.created {id}`, `sandbox.intervention {classification, verdict}`, `sandbox.dryrun.finished {processPassed, ED}`, `sandbox.verdict {choice, checklistDone}`. Никогда не отправлять доходность как метрику рейтинга.

**Безопасность.** Никаких внешних запросов; поля `key/secret` в редакторе всегда маскируются и никогда не сохраняются в телеметрию.

## 11. Сводные критерии приёмки модуля

- [ ] Все пять станций проходимы в учебном режиме за 60–90 минут чистого времени (без dry-run-ожидания — 8 минут внутри).
- [ ] Ворота открываются только артефактами; в свободном режиме — все открыты.
- [ ] Каждый экран имеет «цель одной фразой», задание, момент «ага», артефакт.
- [ ] Числа ⚑ совпадают с уроками (проверочный список в `spec-numbers.json`, тест сверяет константы движка с ним).
- [ ] Один и тот же код стратегии используется в бэктесте и dry-run (архитектурный тест: единственная точка входа `evaluateStrategy`).
- [ ] Ни одна метрика рейтинга/бейджа не зависит от доходности.
- [ ] Автотесты локализации: нет непереведённых токенов вне белого списка; нет ключа конфига/метрики без записи в глоссарии.
- [ ] Экспорт досье воспроизводит структуру репозитория из FT-20.

Поправки к спецификации (erratum)
§7.1.3 и CFG-007: "unit": "candles" не существует в Freqtrade. Допустимые единицы unfilledtimeout.unit — minutes (по умолчанию) и seconds. Учебный конфиг исправлен на "entry": 180, "exit": 180, "unit": "minutes" (= 3 свечи по 1h). Правило CFG-007 пересчитывает таймаут в свечи по таймфрейму из контекста.
Задание «Найди 6 ошибок» не покрывается 15 правилами. Шестая ошибка — «пара в белом списке, которой не было в начале периода» — не ловится ни одним правилом из §7.1.4 (CFG-008 — про динамический список). Добавлено правило CFG-016 (warning): пара залистилась позже начала тестового диапазона. Без него линтер не может подтвердить шестую находку.
Строка Fee в отчёте (SB-3, задание 2). Настоящий Freqtrade не печатает комиссию в SUMMARY METRICS — она видна только в логе перед отчётом (Using fee 0.1000% …) и в JSON-результате. Поэтому лог-заголовок (последние 15–20 строк) — обязательная часть учебного отчёта, а кликабельная «строка Fee» — это строка лога. В текстах ниже так и сделано.

**Как это встроить**

- Рендер `report-N.txt` делать из `keyNumbers` шаблонизатором, а `consistencyRules` прогонять в CI — тогда отчёт, вопросы и подсказки не разъедутся никогда.
- Клик по строке отчёта ищет совпадение `lineMatch` в пределах `section`; неотмеченные строки получают `sharedFeedback.neutralLineDefault`. Так ученик может кликать что угодно и всегда получит осмысленный ответ, а не тишину.

- Порядок «сделки → просадка → метрики → прибыль» блокирует не только маркеры, но и вопросы: `r1-q1…q5` идут строго в этом порядке, чтобы порядок чтения был не лозунгом, а мышечной памятью.
