# ТЗ-E4 · Движок «Ритуал»

**Статус:** спецификация для реализации агентом · **Слой:** сквозной движок (волна W‑A) · **Зависимости:** E5 «Журнал» (мягкая — E4 умеет работать автономно и писать в E5, когда он появится), глоссарий «Ткни в непонятное» (мягкая)
**Уроки‑хозяева:** П1, П2, П5, П7/П29, П8, П9, П11, П12, П14, П17, П19, П33, П44, 5.4, 5.6, FT‑13, FT‑19, FT‑20, FAI‑07 (через «ворота»)

---

## 0. Зачем движок и чего он НЕ делает

### 0.1. Проблема, которую закрывает E4

Курс объясняет 40+ поведенческих правил, но почти все они — **повторяемые действия**, а не знания: «два вопроса перед касанием», «пять галочек в воскресенье», «три строки вечером», «изменение устава вступает завтра». Прочитанное правило не становится привычкой. E4 превращает правило в **ритуал**: повторяемый чек‑лист с расписанием, напоминанием, историей выполнения и «воротами», которые нельзя пройти кликом.

### 0.2. Три роли движка

| Роль | Что делает | Где живёт |
|---|---|---|
| **Расписанный ритуал** | Утро/вечер/воскресенье/1‑е число/квартал: напомнить, провести по шагам, записать, посчитать стрик | Виджет «Сегодня», Календарь |
| **Ритуал по триггеру** | Не по часам, а по событию: рука тянется к кнопке, пришло ночное уведомление, два стопа подряд | Модалка‑перехватчик поверх любого тренажёра |
| **Ворота (gate)** | Последовательность шагов с зависимостями: hyperopt заблокирован, пока не зелёные шаги 1–6; чек‑лист допуска 20/20 | Внутри FT‑тренажёров и Capstone |

### 0.3. Что E4 не делает

- **Не оценивает результат торговли.** Стрик — только за выполнение процесса. Движок принципиально не знает PnL как условие успеха ритуала (кроме поля «результат недели ±» в двойной отметке, где он — просто факт).
- **Не геймифицирует торговлю.** Никаких «наград за N сделок». Стрики есть только у ритуалов наблюдения, разбора и ограничения.
- **Не заменяет журнал (E5).** E4 пишет записи в E5 через хук; хранение и аналитика паттернов — задача E5. До появления E5 движок хранит записи локально в том же формате.
- **Не даёт «пропустить» ворота.** Кнопка «пропустить» существует только у обычных шагов и только с записью причины.

## 1. Методические принципы (обязательны для реализации)

1. **Один ритуал = одно заблуждение.** У каждого шаблона в поле `breaks` записано, какую ошибку он ломает. Это поле показывается ученику при подключении ритуала.
2. **Ученик «прикручивает» ритуал к себе.** Шаблон — заготовка. Время окна, пункты белого списка, планка «достаточно», допустимая серия стопов — ученик вводит сам. Ритуал без персонализации не активируется (см. §7.3).
3. **Числа из текста урока.** Таймер 15 минут (П9), дыхание 4‑4‑6 ×10 (П11), окна 09:00/20:00 по 15 минут (П12), пять галочек (П2), три строки (П8), шкала 1–10 (П19), «вступает завтра, не более одного в неделю» (5.6), 1‑е число месяца и ±5% (5.4), 8 недель и 20/20 (FT‑20). Ничего не выдумывать.
4. **Пропуск — не позор, а данные.** Сообщение о сорванном стрике нейтральное; движок фиксирует пропуск и предлагает возобновить. Никаких «ты подвёл себя».
5. **Ворота закрываются только выполнением условия.** Пункт «lookahead‑analysis зелёный» закрывается либо результатом соответствующего тренажёра, либо ручной отметкой с обязательным вложением (текст вывода команды / дата / число) — но не голым кликом.
6. **Правило полуночи (П5, П12).** Между 00:00 и 06:00 по локальному времени ученика движок не создаёт напоминаний и не даёт запускать ритуалы с шагом типа `decision`, кроме тех, что явно помечены `night_allowed` и входят в белый список.
7. **Русский без английского.** Все подписи, кнопки, названия — на русском. Английские токены (`/forceexit`, `dry_run`, `hyperopt`) допускаются только внутри текста шага и обязаны быть обёрнуты в компонент глоссария (`<Term key="forceexit">`), по клику — русская карточка.
8. **Два времени.** Ритуалы ученика живут в **реальном** времени. Ритуалы внутри тренажёров (например, «8 недель dry‑run» в FT‑20) живут в **симуляционном** времени тренажёра. Движок обязан поддерживать оба через абстракцию `Clock` (§4.6).

## 2. Глоссарий движка

| Термин | Значение |
|---|---|
| **Шаблон ритуала** (`RitualTemplate`) | Неизменяемая заготовка из каталога курса: шаги, расписание по умолчанию, поля персонализации, заблуждение |
| **Подключённый ритуал** (`RitualInstance`) | Шаблон + значения персонализации + расписание ученика. Один ученик может иметь один экземпляр каждого шаблона (кроме `multi: true`) |
| **Прогон** (`RitualRun`) | Одно выполнение ритуала в конкретный момент: ответы по шагам, длительность, статус |
| **Шаг** (`Step`) | Единица прогона: галочка, факт, чипы, число, таймер, метроном, подпись, запись в журнал, ворота |
| **Ворота** (`Gate`) | Шаг с условием закрытия, не зависящим от клика: результат другого интерактива, задержка, вложение |
| **Стрик** (`Streak`) | Число подряд выполненных плановых прогонов; считается только для ритуалов с расписанием |
| **Окно** (`Window`) | Интервал реального времени, в который прогон считается «плановым» (например, 07:00–11:00 для утреннего) |
| **Перехватчик** (`Guard`) | API, через который любой тренажёр запускает ритуал по триггеру перед выполнением действия |
| **Часы** (`Clock`) | Источник времени: реальный (`RealClock`) или симуляционный тренажёра (`SimClock`) |

## 3. Модель данных

Формат — JSON‑сериализуемые объекты. Хранение: локально (IndexedDB/localStorage) с возможностью синхронизации на бэкенд; модель не должна зависеть от способа хранения.

### 3.1. Шаблон ритуала

```ts
interface RitualTemplate {
  id: string;                    // "p1_two_questions"
  version: number;               // для миграций
  title: string;                 // «Два вопроса перед касанием»
  lessons: string[];             // ["П1", "FT-19", "5.5"]
  breaks: string;                // заблуждение, которое ломает
  kind: "scheduled" | "triggered" | "gate";
  multi?: boolean;               // можно ли несколько экземпляров
  schedule?: ScheduleSpec;       // для scheduled
  triggers?: TriggerSpec[];      // для triggered
  personalization: PersonalField[];  // что ученик заполняет при подключении
  steps: StepSpec[];
  completion: CompletionRule;    // что считать выполненным прогоном
  streak?: StreakRule;
  journalHook?: JournalHookSpec; // как писать в E5
  nightAllowed?: boolean;        // можно ли запускать 00:00–06:00
  clock?: "real" | "sim" | "both";
  minDurationSec?: number;       // защита от «прокликал за 3 секунды»
}
```

### 3.2. Расписание

```ts
interface ScheduleSpec {
  cadence: "daily" | "weekly" | "monthly" | "quarterly" | "sim_step";
  windows: Window[];             // для daily может быть два: утро и вечер
  weekday?: 0|1|2|3|4|5|6;       // для weekly (0 = воскресенье)
  dayOfMonth?: number;           // для monthly (1)
  quarterDay?: number;           // для quarterly (1)
  graceHours?: number;           // сколько часов после окна прогон ещё считается плановым
  editableByStudent: ("time" | "weekday")[];
}

interface Window {
  id: string;                    // "morning"
  label: string;                 // «Утреннее окно»
  start: string;                 // "09:00" локальное
  end: string;                   // "11:00"
  remindAt?: string;             // "09:00"
  expectedDurationMin?: number;  // 15
}
```

### 3.3. Триггеры

```ts
type TriggerSpec =
  | { type: "guard"; guardKey: string }          // вызов из тренажёра: ritual.guard("intervene")
  | { type: "event"; event: string; filter?: object } // событие шины: "trainer.stop_hit", count>=2
  | { type: "manual"; buttonLabel: string };     // кнопка «хочу войти» в панели ученика
```

### 3.4. Поля персонализации

```ts
interface PersonalField {
  key: string;                   // "whitelist"
  label: string;                 // «Что вправе меня разбудить»
  type: "text" | "number" | "time" | "list" | "choice" | "percent";
  required: boolean;
  min?: number; max?: number;    // например list: min 2, max 3 (П5)
  defaults?: unknown;            // подсказка из урока, но не автозаполнение
  hint: string;                  // объяснение своими словами из урока
  lockedAfterActivation?: boolean;   // нельзя менять «сегодня» (5.6)
  changePolicy?: "next_day" | "next_week" | "quarterly";
}
```

### 3.5. Шаги

```ts
type StepSpec =
  | { type: "check"; id: string; text: string; required: boolean }
  | { type: "fact"; id: string; prompt: string; minChars: number; forbidPatterns?: string[]; required: true }
  | { type: "yesno"; id: string; prompt: string; onYes?: StepAction; onNo?: StepAction }
  | { type: "chips"; id: string; prompt: string; options: Chip[]; min: number; max: number; freeText?: boolean }
  | { type: "number"; id: string; prompt: string; unit?: string; min?: number; max?: number; compareTo?: string }
  | { type: "scale"; id: string; prompt: string; from: number; to: number; labels?: Record<number,string> }
  | { type: "timer"; id: string; seconds: number; text: string; skippable: false }
  | { type: "breath"; id: string; inhale: number; hold: number; exhale: number; cycles: number }
  | { type: "sign"; id: string; text: string; delayUntil?: "next_day" | "24h" | "next_monday"; secondPerson?: boolean }
  | { type: "journal"; id: string; entryType: JournalEntryType; fields: string[] }   // запись в E5 из ответов
  | { type: "gate"; id: string; text: string; condition: GateCondition; dependsOn?: string[] }
  | { type: "info"; id: string; text: string };   // напоминание из урока, без ответа

interface StepAction { type: "block" | "allow" | "goto" | "journal" | "message"; payload?: unknown }
interface Chip { key: string; label: string; lesson?: string }
```

### 3.6. Условия ворот

```ts
type GateCondition =
  | { type: "external"; source: string; key: string; expect: unknown }   // результат другого интерактива
  | { type: "attachment"; kind: "text" | "number" | "date"; validate?: string }  // ручная отметка с вложением
  | { type: "delay"; from: "opened" | "prevStepClosed"; hours: number }   // «вступает завтра»
  | { type: "count"; event: string; atLeast: number; sinceDays?: number } // «журнал ведётся 2+ недели»
  | { type: "streak"; ritualId: string; atLeast: number }                 // «регламент соблюдён 2 недели»
  | { type: "all"; of: GateCondition[] } | { type: "any"; of: GateCondition[] };
```

### 3.7. Прогон, стрик, история

```ts
interface RitualRun {
  id: string; instanceId: string; templateId: string;
  clock: "real" | "sim";
  startedAt: string; finishedAt?: string;   // ISO; для sim — метка симуляции
  windowId?: string;                        // в какое окно попал
  status: "completed" | "partial" | "abandoned" | "blocked" | "skipped";
  planned: boolean;                         // попал в окно/грейс
  answers: Record<string, unknown>;         // stepId → ответ
  durationSec: number;
  outcome?: "allowed" | "blocked";          // для triggered
  skipReason?: string;
  journalEntryIds?: string[];
}

interface Streak {
  instanceId: string;
  current: number; best: number;
  lastPlannedRunAt?: string;
  missedInRow: number;
  history: { periodKey: string; done: boolean }[];   // "2026-08-14", "2026-W33", "2026-08"
}
```

### 3.8. Экземпляр

```ts
interface RitualInstance {
  id: string; templateId: string; templateVersion: number;
  activatedAt: string;
  personal: Record<string, unknown>;
  schedule?: ScheduleSpec;                  // после правок ученика
  pendingChanges: { field: string; value: unknown; effectiveAt: string; reason: string }[];  // 5.6
  status: "active" | "paused" | "archived";
  streak?: Streak;
}
```

## 4. Ядро движка (поведение)

### 4.1. Жизненный цикл прогона

```
ожидание → [напоминание] → открыт → шаг 1 … шаг N → завершение
                                    ↘ прерван (abandoned, сохраняются ответы)
                                    ↘ заблокирован (blocked — для triggered)
```

- Прогон **сохраняется после каждого шага** (черновик). Возврат через час продолжает с того же места, если окно ещё открыто; иначе черновик помечается `partial`.
- Прогон считается `completed`, только если выполнена `completion` шаблона (по умолчанию — все `required` шаги) **и** `durationSec ≥ minDurationSec`. Если быстрее — статус `partial` с подсказкой: «Прогон занял 12 секунд. Ритуал засчитывается от 90 секунд: перечитай пункты».

### 4.2. Плановость и грейс

Прогон **плановый**, если `startedAt` ∈ окно или ∈ окно + `graceHours`. Для еженедельных: в назначенный день ± 1 день. Внеплановые прогоны сохраняются, идут в историю, но **не продлевают стрик**.

### 4.3. Стрик

- Считается по `periodKey` (день / ISO‑неделя / месяц). Один плановый completed‑прогон за период → период закрыт.
- Пропуск периода → `current = 0`, `missedInRow += 1`. Сообщение: «Вчерашнее окно пропущено. Стрик начинается заново — это факт, а не оценка. Сегодняшнее окно: 20:00–22:00».
- Нет «заморозок», нет покупки пропусков. Есть **пауза** ритуала (например, отпуск): в паузе периоды не считаются пропусками, стрик не растёт.
- `best` — лучший стрик, показывается рядом с текущим.

### 4.4. Напоминания

- Канал: внутриприложенческий баннер + браузерный push (если разрешён). Одно напоминание на окно в `remindAt`, повтор через 60 минут, если прогон не открыт и окно ещё активно. Максимум 2 напоминания на окно.
- **Запрет ночью:** 00:00–06:00 напоминания не отправляются, кроме ритуалов с `nightAllowed: true`, у которых триггер входит в белый список ученика (§6, ритуал П5).
- Воскресный осмотр напоминает утром воскресенья (09:00) и повторно в 18:00, если не сделан.
- Ежемесячные/квартальные: напоминание за день («Завтра 1‑е число: ребалансировка») и в день.

### 4.5. Политика изменений (из 5.6)

Поля с `changePolicy` меняются **не мгновенно**: правка записывается в `pendingChanges` с `effectiveAt`. До наступления срока движок использует старое значение и показывает: «Изменение вступит в силу завтра, 15 августа». Для `next_week` — понедельник. Отменить отложенное изменение можно в любой момент. Причина изменения — обязательное текстовое поле (минимум 20 символов).

Дополнительно: экземпляр ритуала «Устав как код» (§6.12) держит счётчик изменений за неделю; второе изменение блокируется: «Правило одного изменения: эффект первого ещё не измерен. Следующее окно правок — в понедельник».

### 4.6. Два времени: `Clock`

```ts
interface Clock { now(): string; kind: "real" | "sim"; periodKey(cadence): string; onTick(cb): Unsub }
```

- `RealClock` — системное время, локальный часовой пояс ученика (спрашивается один раз, хранится).
- `SimClock` — создаётся тренажёром (например, FT‑20 «Восемь недель dry‑run», где «неделя» = шаг симуляции). Тренажёр вызывает `simClock.advance("1w")`; движок пересчитывает плановые периоды, генерирует прогоны и стрики **внутри контекста тренажёра**, не смешивая с реальными.
- Экземпляры с `clock: "sim"` хранятся в неймспейсе тренажёра (`scope: trainerId`) и не показываются в личном виджете «Сегодня».

### 4.7. Перехватчик (`guard`)

API для любого тренажёра:

```ts
const res = await ritual.guard("intervene", {
  trainerId: "ft19_night_console",
  action: "/forceexit all",           // что собирался сделать ученик
  context: { time: "02:40", pnl: -2.5, worldEvents: [] }
});
// res: { allowed: boolean; runId: string; reason?: "no_fact" | "wait_till_morning" | "not_in_whitelist" }
```

- Если у ученика не подключён ритуал с этим `guardKey`, движок запускает **встроенную минимальную версию** (для П1 — те же два вопроса без персонализации) и предлагает подключить полноценный после прогона.
- Тренажёр обязан **уважать** `allowed: false` (не выполнять действие) и показать сообщение движка.
- Каждый вызов guard пишет `RitualRun` с `outcome`, а при `allowed: true` — запись в журнал вмешательств (E5, тип `intervention`).

### 4.8. Шина событий

Движок подписывается на события тренажёров и сам их публикует:

| Событие | Кто публикует | Кто слушает |
|---|---|---|
| `trainer.stop_hit {trainerId, count}` | тренажёры сделок | ритуал «Стоп‑тильт» (П14): 2 системных стопа подряд → предложение запустить |
| `trainer.urge_to_enter` | кнопка «хочу войти» | «Холодный таймер» (П9) |
| `trainer.panic_drop {pct}` | тренажёры обвала | «Красный экран» (П11) |
| `trainer.night_alert {kind}` | FT‑19, П5 | «Радионяня» (П5): фильтрация по белому списку |
| `ritual.run.completed {templateId}` | E4 | E5, метрики, гейты других ритуалов |
| `ritual.gate.closed {gateId}` | E4 | тренажёры (разблокировать hyperopt и т.п.) |
| `external.result {source, key, value}` | любой интерактив | ворота с `condition.type = "external"` |

## 5. Интерфейс: экраны и компоненты

### 5.1. Виджет «Сегодня» (главная / панель ученика)

- Список ритуалов на сегодня в порядке окон: утро → день → вечер. Карточка: название, окно, стрик (🔥 не использовать — рисовать нейтральную полоску дней), кнопка «Провести».
- Отдельный блок «По триггеру»: кнопки ручного запуска — «Хочу вмешаться», «Хочу войти в сделку», «Мне плохо после стопов». Каждая запускает соответствующий ритуал.
- Индикатор «Ночной режим» с 00:00 до 06:00: виджет затемняется, вместо кнопок — текст «Правило полуночи: решения не принимаются. Белый список: [пункты ученика]».

### 5.2. Экран прогона

- Один шаг на экран (мобильный) или вертикальный чек‑лист с раскрывающимися шагами (десктоп). Прогресс «шаг 3 из 5».
- У шага `fact`: поле с живой валидацией. Запрещённые формулировки (`forbidPatterns`) подсвечиваются: если ученик пишет «страшно», «не нравится», «кажется», «чую» — поле красное с подсказкой «Это состояние головы, а не факт мира. Факт — это «нет связи с биржей 15 минут», «цены в боте не совпадают с биржей», «я сам менял код»».
- У шага `timer`: крупный обратный отсчёт, кнопки «пауза» нет. Текст под таймером — из урока («стакан воды, 10 глубоких выдохов»). Закрытие вкладки не сбрасывает таймер (хранится `startedAt`).
- У шага `breath`: визуальный метроном — круг расширяется 4 с, держится 4 с, сжимается 6 с; счётчик циклов 1/10. Текст: «Вдох носом 4 — задержка 4 — выдох ртом 6».
- У шага `gate`: серый замок, текст условия, статус «закрыто: ждём результат тренажёра «Смести окно — сломай телепата»» / кнопка «Приложить результат» (для `attachment`).
- У шага `sign`: поле подписи (ввод имени) + дата; если `delayUntil` — кнопка неактивна до срока с обратным отсчётом «Подписать можно завтра с 06:00».

### 5.3. Конструктор подключения ритуала

Мастер из 3 экранов: (1) «Какую ошибку ломает» + пункты урока; (2) персонализация — поля из `personalization`, с подсказками, без автозаполнения дефолтами (дефолты показываются серым как пример); (3) расписание — время окон (только в разрешённых пределах) и подтверждение «Подключить».

Кнопка «Подключить» неактивна, пока `required` поля пусты.

### 5.4. История и календарь

- Календарь месяца: клетки — дни; заливка по выполнению плановых прогонов; клик по дню — список прогонов с ответами.
- Для еженедельных — сетка недель. Для «Двойной отметки недели» — две полоски в клетке: результат (± серым, без цвета «хорошо/плохо») и процесс (зелёный/красный).
- Фильтр по ритуалу. Экспорт CSV.

### 5.5. Сводка недели (воскресенье)

Автоматически генерируется по данным E4 (и E5, если есть): число плановых прогонов / выполненных; число вызовов guard и доля «заблокировано без факта»; для «трёх строк» — облако чипов эмоций; напоминание про воскресный осмотр.

### 5.6. Микрокопи (обязательные тексты)

| Ситуация | Текст |
|---|---|
| Успешный прогон | «Готово. Это прогон № 14, плановых подряд — 9.» |
| Сорванный стрик | «Окно пропущено. Счётчик начинается заново — это данные, а не оценка.» |
| Слишком быстрый прогон | «Прогон занял N секунд. Засчитывается от 90: перечитай пункты.» |
| Guard заблокировал (нет факта) | «Факт не назван — руки прочь. Уведомление — не приказ действовать. Записано в журнал.» |
| Guard заблокировал (подождёт до утра) | «Ты сам ответил: решение подождёт. Утреннее окно — 09:00. Записано в журнал.» |
| Guard разрешил | «Факт назван: «…». Действие разрешено. Через 7 дней движок спросит, чем это закончилось.» |
| Ночной режим | «00:00–06:00: решения не принимаются. Белый список: …» |
| Отложенное изменение | «Изменение вступит в силу завтра, {дата}. Причина: «…»» |
| Ворота закрыты | «Пункт закрывается результатом, а не галочкой: {условие}» |

## 6. Каталог предустановленных ритуалов (v1)

Ниже — 15 шаблонов. Для каждого: id, тип, заблуждение, персонализация, шаги, завершение, журнал. Тексты шагов — из уроков.

### 6.1. `p1_two_questions` — «Два вопроса перед касанием» (П1, FT‑19, 5.5)

- **Тип:** triggered, `guardKey: "intervene"`, `nightAllowed: true` (но с проверкой белого списка, см. onYes).
- **Ломает:** «тревога — это информация», «ну тут‑то точно надо было вмешаться».
- **Персонализация:** нет (работает сразу), рекомендует подключить `p5_whitelist`.
- **Шаги:**
  1. `info`: «Есть одна уважительная причина трогать бота — изменился мир. Мир: данные, биржа, интернет, код, законы, деньги. Голова: страх, жадность, скука, новости, чужие скриншоты.»
  2. `fact` (minChars 25, forbidPatterns: `страшно|боюсь|кажется|чую|не нравится|интуиц|минус на экране|цена против`): «Вопрос 1. Назови факт: что конкретно изменилось в мире?» → пусто/запрещённое → `block`.
  3. `chips` «мир или голова?» — обязателен выбор `мир` / `голова`; `голова` → `block` с текстом «Тревога ощущается как информация. Это будильник в голове».
  4. `yesno`: «Вопрос 2. Если я приму это решение завтра утром выспавшимся — оно будет тем же?» → «Да» → `block` с текстом «Значит, подождёт до утра»; «Нет, к утру будет поздно» → продолжить.
  5. Если `RealClock` показывает 00:00–06:00 и подключён `p5_whitelist`: `gate external` — факт должен совпасть с одним из пунктов белого списка (ученик выбирает пункт из своего списка или «не входит» → `block`).
  6. `journal` → E5 `intervention` {дата, «мир/голова», факт, действие, `followUpAt: +7d`}.
- **Завершение:** любой исход (`allowed`/`blocked`) — прогон completed. `minDurationSec: 20`.
- **Follow‑up:** через 7 дней движок открывает мини‑прогон: «Неделю назад ты вмешался: «…». Чем закончилось?» — `chips`: сэкономило / стоило денег / нейтрально + число. Это пишется в ту же запись E5. Сводка по П1: «девять из десяти таких спасений стоили денег» проверяется на данных ученика.

### 6.2. `p5_whitelist` — «Белый список ночи» (П5, FT‑19)

- **Тип:** scheduled (weekly, воскресенье — пересмотр) + служебный (фильтр событий).
- **Ломает:** «уведомление = приказ действовать», «гляну одним глазком».
- **Персонализация:** `whitelist: list` (min 2, max 3), подсказки из урока: «нет связи с биржей больше 15 минут», «сработала аварийная кнопка», «бот отправил приказ, которого не мог отправить». Поле `quietHours` фиксировано 00:00–06:00 (не редактируется — правило полуночи). `checkWindows`: два времени (по умолчанию пусто; пример 09:00 и 20:00).
- **Шаги еженедельного пересмотра:** `check` × N по каждому пункту «Пункт всё ещё описывает факт мира?», `yesno` «Добавить/убрать?» (правка — с `changePolicy: next_day`).
- **Служебное поведение:** все `trainer.night_alert` фильтруются: если `kind` не в списке — тренажёр получает `suppressed: true`, а ученику показывается только утренняя сводка: «Ночью пришло N уведомлений. Требовали действий: 0. Все ушли в сводку». Если в списке — разрешён запуск `p1_two_questions`.
- **Журнал:** утренняя сводка → E5 `night_digest` {count, actionable}.

### 6.3. `p12_two_windows` — «Два окна проверки» (П12, П5, FT‑19)

- **Тип:** scheduled, daily, два окна.
- **Ломает:** «держу руку на пульсе» (частый просмотр), «вечерняя гениальная идея».
- **Персонализация:** `morning: time` (диапазон 06:00–12:00), `evening: time` (диапазон 17:00–23:00), `expectedDurationMin: 15` фиксировано.
- **Шаги утреннего окна:** `check` «Прочитал сводку за ночь» · `check` «Проверил журнал ошибок бота» · `yesno` «Есть факт изменения мира?» → да → запуск `p1_two_questions`.
- **Шаги вечернего окна:** `check` «Посмотрел итог дня (/profit) один раз» · `info` «Запрет вечерних правок: любые изменения кода, настроек и устава — только утром» · `yesno` «Появилась идея что‑то поменять?» → да → `fact` «Запиши идею одной фразой» → `journal` E5 `idea_parking` («Утренний прогон покажет её тебе») — правка блокируется.
- **Утром следующего дня:** движок показывает припаркованные идеи: «Вчера в 21:30 ты записал: «…». На свежую голову — оставить или удалить?»
- **Стрик:** за день засчитывается при выполнении обоих окон; при одном — период «наполовину» (отдельный цвет), стрик не рвётся, но и не растёт.

### 6.4. `p8_three_lines` — «Три строки вечером» (П8, П19)

- **Тип:** scheduled, daily, вечернее окно (общее с 6.3, можно объединять в один прогон — см. §7.4 «связки»).
- **Ломает:** «оцениваю себя по счёту дня», накопленная эмоция.
- **Персонализация:** `evening: time`.
- **Шаги:**
  1. `fact` (minChars 10): «1. Какое главное решение сегодня принял?»
  2. `chips` + `fact`: «2. Почему — какой пункт правил или какая эмоция им руководила?» — чипы `правило устава` / `эмоция`; при `эмоция` — обязательный выбор чипа эмоции.
  3. `chips` (ровно 1, freeText): «3. Что чувствовал до и после — одним словом» — чипы: спокойствие, тревога, скука, азарт, злость, облегчение, стыд, гордость.
  4. `scale` 1–10 (П19): «Уровень напряжения перед закрытием ноутбука». Подписи: 1–2 «полное спокойствие», 6 «скрытое напряжение», 9–10 «срыв». При ≥6 → `info` «Не садись за терминал завтра с этим грузом» + предложение запустить 6.11 (дебрифинг) или физическую разгрузку из П13 (20–30 минут ходьбы).
  5. `journal` → E5 `daily_three_lines`.
- **Через 7 записей:** движок генерирует «карту паттернов»: распределение эмоций по дням недели и времени, доля «эмоция» против «правило». Показывается в сводке воскресенья.
- `minDurationSec: 90`.

### 6.5. `p2_sunday_five` — «Воскресный осмотр — пять галочек» (П2, 5.4)

- **Тип:** scheduled, weekly, воскресенье, окно 09:00–21:00.
- **Ломает:** слепая вера в автоматику (automation bias) и вечное сомнение (algorithm aversion).
- **Персонализация:** `sundayTime`, `usualDrawdownPct: percent` («привычная болтанка» — берёт из бэктеста/тренажёра), `costsBaselineBps: number`.
- **Шаги** (каждый — `check` + поле значения, галочка без значения не принимается):
  1. «Журнал ошибок пуст?» — `number` «ошибок за неделю».
  2. «Сделки совпадают с задуманным планом?» — `number` «сделок вне плана».
  3. «Результат похож на проверенный на истории — в пределах привычной болтанки?» — `percent` результата недели; движок сравнивает с `usualDrawdownPct` и подсвечивает «в пределах / вне».
  4. «Расходы на сделки не поползли вверх?» — `number` bps за круг; сравнение с `costsBaselineBps`.
  5. «Не поменяли ли правила биржа или инструмент?» — `yesno` + `fact` при «да».
  6. `info`: «Пять галочек — работаем дальше. Пересмотр стратегии — по расписанию из устава, как замена масла, а не по настроению плохой недели».
  7. При ответах вне нормы: `info` «Это повод для планового разбора, не для ручного вмешательства» + ссылка на `p1_two_questions`.
  8. `journal` → E5 `weekly_inspection`.
- **Связка с 5.4:** дополнительный `check` «Аудит журналов и инцидентов (сетевые задержки, сбои исполнения)» — еженедельный пункт из таблицы урока 5.4.

### 6.6. `p8_double_mark` — «Двойная отметка недели» (П8, П33)

- **Тип:** scheduled, weekly, воскресенье (идёт следом за 6.5).
- **Ломает:** «прибыльная неделя с нарушением — хорошая неделя».
- **Шаги:**
  1. `chips`: «Результат недели» — `+` / `−` / `0` (без окраски).
  2. `yesno`: «Устав соблюдён полностью?» → «нет» → `chips` нарушений (ручная сделка, изменил размер, вмешался без факта, пропустил окно, вечерняя правка, другое+текст) + `number` «сколько раз».
  3. `info` — вердикт движка: процесс чист → «Отличная неделя» (даже при «−»); нарушение → «Плохая неделя — независимо от знака. Нарушения растут как трещины: чини забор» (даже при «+»).
  4. `number` авто: **Process Score** = доля недель за последние 12 с чистым процессом; цель из П33 — > 95 %.
  5. `journal` → E5 `weekly_double_mark`.
- **История:** в клетке недели две полоски (см. §5.4). Демонстрационная фраза при первой прибыльной неделе с нарушением: «+2 % с нарушением — эту неделю повторить нельзя (повезло). −1 % по уставу — можно всегда».

### 6.7. `p9_cold_timer` — «Холодный таймер 15 минут» (П9, П14)

- **Тип:** triggered (`manual` «Хочу войти прямо сейчас», `event trainer.urge_to_enter`).
- **Ломает:** «поезд уедет навсегда».
- **Шаги:**
  1. `info`: «Встань из‑за стола, убери руки от клавиатуры и мыши».
  2. `timer` 900 с, текст: «Пик дофаминовой волны физиологически спадает за 15 минут. Выпей стакан воды. Сделай 10 глубоких выдохов».
  3. `breath` 4‑4‑6 × 10 (необязательный, кнопка «сделать дыхание сейчас»).
  4. `yesno`: «Открой устав. Есть ли сигнал по твоей системе?» → «нет» → `info` «Закрой вкладку. Поезда ходят каждые пять минут» → `block`; «да» → `fact` «Какой пункт устава даёт сигнал?» → `allow`.
  5. `journal` → E5 `urge` {результат, эмоция до/после `scale`}.
- В тренажёрах кнопка «купить» после `block` остаётся неактивной 15 минут симуляционного/реального времени тренажёра.

### 6.8. `p11_red_screen` — «Красный экран» (П11)

- **Тип:** triggered (`event trainer.panic_drop pct≥10`, `manual` «Рынок падает, трясёт»).
- **Ломает:** «надо срочно что‑то делать».
- **Шаги:** `info` «Категорический запрет на ручные сделки. Руки от мыши» → `breath` 4‑4‑6 × 10 → `check` «Все защитные функции исполняются ботом или стоп‑ордерами» → `info` «Человек в состоянии паники к терминалу не допускается. Кортизол держится 2–4 часа» → `scale` 1–10 «пульс/тревога сейчас» → `journal` E5 `panic_episode`.
- После прогона тренажёр получает `allowed: false` для любых ручных сделок на 4 симуляционных часа.

### 6.9. `p14_stop_tilt` — «Стоп‑тильт: 4 часа» (П14)

- **Тип:** triggered (`event trainer.stop_hit count≥2 within session`, `manual` «Хочу отыграться»).
- **Ломает:** «сделаю одну быструю сделку, верну свои 5 тысяч».
- **Шаги:** `info` «Два системных стопа подряд или один внесистемный срыв — протокол Стоп‑Тильт» → `check` «Закрыл все торговые вкладки» → `check` «Телефон в режиме «Не беспокоить»» → `sign` с `delayUntil: 4h` «Покидаю рабочее место минимум на 4 часа: прогулка, душ, тренировка» → `info` «Запрет на открытие любых сделок до следующего утра» → `journal` E5 `tilt_stop`.
- Движок публикует `ritual.lock {scope: trainerId, until: nextMorning06}`; тренажёры блокируют кнопки сделок.

### 6.10. `p17_daily_limit` — «Дневной лимит сделок» (П17)

- **Тип:** scheduled (daily, служебный счётчик) + gate в тренажёрах ручной торговли.
- **Ломает:** «больше сделок — больше денег».
- **Персонализация:** `maxTradesPerDay: number` (1–2, подсказка из урока), `dailyTargetPct: 3`, `dailyLossPct: 1.5` (редактируемо в пределах ±50 %, `changePolicy: next_day`).
- **Поведение:** тренажёры перед каждой сделкой вызывают `ritual.guard("trade_limit")`; при достижении лимита — `block` с текстом «Сделал план — закрой экран. Терминал заблокирован до завтра». Счётчик показывает «комиссионную эрозию»: 80 сделок/мес против 4 — иллюстрация из урока (Трейдер А +5,8R / Трейдер Б −14R).

### 6.11. `p19_debrief` — «Вечерний дебрифинг после убыточного дня» (П19, П18)

- **Тип:** triggered (`event trainer.day_closed pnl<0`, `manual` «День закрылся минусом»).
- **Ломает:** «захлопнуть ноутбук и лечь с грузом».
- **Шаги:** `scale` 1–10 «напряжение сейчас» → 5 минут таймер письменного дебрифинга (`timer` 300, не блокирующий поле ввода) с полями протокола MHH из П18: `fact` «Что произошло (конкретно)» → `fact` «Почему в тот момент это казалось правильным» → `fact` «Коренная ошибка» → `fact` «Объективная реальность рынка» → `fact` «Инъекция логики — короткая фраза для терминала» → `scale` 1–10 «напряжение после» → `journal` E5 `debrief_mhh`.
- Инъекции логики копятся в «стикеры»: движок показывает случайную из них при открытии любого тренажёра сделок (перекликается с П18).

### 6.12. `c56_charter_as_code` — «Устав: правило одного изменения» (5.6, FT‑17, FT‑20)

- **Тип:** gate + служебная политика изменений.
- **Ломает:** «поправлю настройки сейчас, пока помню».
- **Персонализация** (все `lockedAfterActivation` с `changePolicy: next_day`): `riskPerTradePct` (подсказка 1,0), `dailyLossLimitPct` (3,0), `maxGrossExposurePct` (60), `maxLeverage` (2), `killCriteria: {rollingSharpe60dBelow: 0.3, drawdownPctAbove: 18, execDevPctAbove: 25}`, `profitWithdrawalPct` (25 % за квартал), `maxChangesPerWeek: 1` (не редактируется).
- **Поведение:** любая правка любого поля → `pendingChanges` с `effectiveAt: next_day` + обязательная причина + ожидаемый эффект; второе изменение за ISO‑неделю → блок. Экспорт в формат `charter.yaml` (для E2 «Живой конфиг»); импорт значений из E2. История правок — git‑подобный лог: дата, поле, было → стало, причина, эффект по факту (заполняется через 4 недели follow‑up‑прогоном).
- **Квартальный прогон:** 1‑го числа квартала — «Правило вывода прибыли: 25 % прибыли квартала выводится на банковский счёт» (`check` + `number`) + «Перечитать письмо из будущего» (см. 6.13).

### 6.13. `p7_letter_from_future` — «Письмо из будущего + предохранители» (П7, П29)

- **Тип:** одноразовый конструктор + quarterly перечитывание.
- **Ломает:** «со мной такого не случится».
- **Шаги конструктора:** выбор из 8 типовых причин урока П7 (выключил бота на просадке; увеличил размер после серии; вмешался ночью без факта; одному инструменту слишком много места; не заметил поломку без осмотра; взял чужой совет; снял «на радостях» половину; тянул с налогами) + свободные; для каждой — предохранитель: `fact` правило, `number` число, `chips` где зашито (устав / код / API). Минимум 5 причин и 5 предохранителей (П29). `sign` с датой.
- **Quarterly:** 1‑го числа квартала, 15 минут: перечитать (текст показывается), `check` по каждому предохранителю «действует», `yesno` «был серьёзный сбой — дополнить?» → новая причина.
- **Связь:** предохранители, помеченные «устав», предлагаются к добавлению в `c56_charter_as_code`.

### 6.14. `ft13_anti_liar` — «Конвейер анти‑лжец» (FT‑13, FT‑11, FT‑12, 1.9)

- **Тип:** gate, `clock: both`, `multi: true` (по одному на стратегию — поле `strategyName`).
- **Ломает:** «сначала hyperopt, проверки потом».
- **Шаги‑ворота с зависимостями** (порядок урока):
  1. «Данные проверены (непрерывность, дубли)» — `external` источник `ft08_data_gaps` или `attachment text` (вывод `check_data.py` со словом PASS).
  2. «lookahead‑analysis — зелёный» — `external ft11_shift_window` / `attachment text`.
  3. «recursive‑analysis — зелёный» — `external ft12_warmup` / `attachment`.
  4. «Бэктест с честным fee + оценка проскальзывания прогоном с завышенным fee» — `attachment number` ×2 (PF при базовом и при завышенном fee).
  5. «Соседние таймфреймы» — `attachment`.
  6. «Робастность ±20 %» — `external m39_plateau` / `attachment number` ×3 (PF при −20 % / база / +20 %); движок проверяет падение ≤ 20 % (1.12).
  7. «hyperopt» — `dependsOn: [1..6]`; пока не закрыты — замок и текст «Оптимизация заблокирована: шаги 1–6 не зелёные». После — `dependsOn` шаг 8.
  8. «OOS‑проверка после hyperopt» — `attachment number` OOS‑PF; подсказка «здоровый OOS = 50–70 % от in‑sample; лучше — ищи утечку» (FT‑16).
- Событие `ritual.gate.closed {gateId:"hyperopt"}` разблокирует кнопку оптимизации в тренажёре FT‑16 «4096 монеток».
- Повторная правка стратегии (событие `strategy.changed`) → ворота 2–8 переоткрываются с текстом «После каждой правки протокол повторяется: утечка легко возвращается».

### 6.15. `ft20_dry_run_8w` + `ft20_go_live_20` — «Восемь недель dry‑run» и «Чек‑лист допуска 20/20» (FT‑20, 4.5, 5.1)

- **Тип:** `ft20_dry_run_8w` — scheduled `sim_step` (в тренажёре) **или** weekly real (для реального dry‑run ученика); `ft20_go_live_20` — gate.
- **Ломает:** «19/20 — почти готов», «dry‑run — формальность».
- **Недельный прогон (8 раз):** `number` uptime %, `number` сигналов факт / ожидание (движок считает расхождение; > 30 % — красный флаг), `number` Execution Deviation % (< 10 норма, 10–25 серая зона, > 25 стоп — из 4.5), `number` вмешательств, `check` «каждое вмешательство имело факт «мир»» (проверяется по журналу E5 `intervention`: если есть запись с «голова» и `allowed` — галочка недоступна), `scale` 1–10 эмоция (П41), `journal` E5 `dryrun_week`. Недели 4–5 — дополнительный `fact` «Как я переживаю плоский период / всплеск» (репетиция П5).
- **Чек‑лист допуска — 20 ворот по блокам урока** (все `required`, каждый с датой закрытия):
  - Бэктест (7): lookahead зелёный; recursive зелёный; fee честный + проскальзывание оценено; 100+ сделок (`attachment number ≥ 100`); OOS пройден; робастность ±20 %; стресс‑тест 3.6 — большинство закрываются `external` из `ft13_anti_liar`.
  - Инфраструктура (6): dry‑run 4+ недели непрерывно (`count dryrun_week ≥ 4`); рестарты не требуются; логи ротируются; Telegram и FreqUI работают; VPS/Docker готов; kill‑switch описан и протестирован (`attachment date`).
  - Риск (4): stake 1–2 % (`external` из E2/устава: `riskPerTradePct ≤ 2`); суммарный риск 4–6 %; protections из риск‑правил; стоп и ROI не менялись после финального бэктеста (`count strategy.changed since finalBacktest = 0`).
  - Оператор (5 → сжаты в счёт до 20): журнал ведётся (`count intervention/dryrun_week`); каждое вмешательство с фактом «мир» (`external E5`); устав написан и подписан (`streak c56 active`); регламент наблюдения соблюдён 2+ недели (`streak p12_two_windows ≥ 14`); доверенное лицо знает про kill‑switch (`attachment text`).
  - Юридика (2) и Психология (2): налоговая модель понята; документы сохраняются; готовность к −N % недели письменно (`fact` + `sign`); сумма микро‑лайва — та, потерю которой допускаешь (`number` и `percent` от капитала ≤ 5 % по 5.1).
  - Точное распределение до 20 пунктов задаётся в JSON‑каталоге; сумма обязана быть ровно 20.
- **Финальное решение:** прогон `sign` с `delayUntil: next_day, 06:00` — «Решение принимает инвесткомитет из тебя завтрашнего: утром, письменно». При 19/20 кнопка «Перейти к микро‑лайву» отсутствует; вместо неё «Продлить dry‑run» и три ловушки самообмана из урока как чипы, помеченные красным: «сделок мало, но все удачные», «перенесу на пару недель, потом доработаю стопы», «депозит маленький, чек‑лист для больших».

## 7. Правила конфигурации и связки

### 7.1. Каталог

Все шаблоны — в `rituals/catalog/*.json`, валидируются схемой при сборке. Тексты — отдельные ключи `i18n/ru/rituals.json` (единственная локаль, но структура готова к другим). Английские токены помечаются `{{term:forceexit}}` и рендерятся компонентом глоссария.

### 7.2. Подключение по мере прохождения

- При завершении урока‑хозяина приложение показывает карточку «Подключить ритуал урока» (без автоподключения).
- `p1_two_questions` доступен как встроенный guard с первого тренажёра с кнопкой вмешательства, даже если урок П1 не пройден (см. §4.7).
- Рекомендуемый порядок подключения (подсказки): П1 → П5 → П8 → П2 → П12 → 5.6 → FT‑13 → FT‑20.

### 7.3. Персонализация обязательна

Экземпляр не активируется без `required` полей. Дефолты из урока показываются как пример, не подставляются. Исключение — `p1_two_questions` (нет полей).

### 7.4. Связки прогонов

Если у нескольких ритуалов совпадает окно (вечернее: 6.3 + 6.4; воскресное: 6.5 + 6.6), движок предлагает один объединённый прогон «Вечерний ритуал (2 части)», сохраняя отдельные `RitualRun` и стрики.

### 7.5. Приоритеты триггеров

Одновременный триггер нескольких ритуалов (например, `panic_drop` и `urge_to_enter`) — по приоритету: `p11_red_screen` > `p14_stop_tilt` > `p1_two_questions` > `p9_cold_timer`. Остальные ставятся в очередь после завершения первого.

### 7.6. Блокировки (`ritual.lock`)

Блокировка действий в тренажёрах — объект `{scope, actions, until, source}`; тренажёры обязаны опрашивать `ritual.isLocked(scope, action)` перед исполнением. Блокировка снимается по времени соответствующих часов (`SimClock` для тренажёра, `RealClock` для личных ритуалов) — никогда кнопкой.

## 9. Уведомления и приватность

- Разрешение на push спрашивается только после первого подключённого scheduled‑ритуала, с объяснением: «Напомню один раз в начале окна и один раз через час. Ночью — никогда».
- Часовой пояс — из браузера, подтверждается пользователем; смена пояса не рвёт стрики (пересчёт `periodKey` по локальной дате).
- Все данные ритуалов — личные; экспорт и удаление по запросу ученика. Текст фактов не отправляется в аналитику (только флаги и длины).

## 11. Критерии приёмки (обязательные тест‑сценарии)

1. **Guard без факта.** В тренажёре FT‑19 клик `/forceexit` в 02:40 при пустом факте → действие не выполнено, показано сообщение из §5.6, создана запись `intervention` с «голова», `outcome: blocked`.
2. **Guard с запрещённой формулировкой.** Факт «мне страшно, минус 3 %» → поле красное, продолжить нельзя.
3. **Guard с фактом.** Факт «нет связи с биржей 20 минут, лог показывает ошибки API» + «мир» + «нет, к утру поздно» + пункт белого списка → `allowed`, follow‑up создан на +7 дней.
4. **Правило полуночи.** В 01:00 виджет «Сегодня» не показывает кнопок ритуалов с шагом `decision`; напоминания не отправляются; `p1_two_questions` доступен только через guard.
5. **Стрик.** Три подряд вечерних прогона в окне → стрик 3; пропуск дня → 0, `best` = 3, сообщение нейтральное; прогон вне окна → сохранён, стрик не изменился.
6. **Слишком быстрый прогон.** Три строки за 15 секунд → `partial`, стрик не растёт, подсказка про 90 секунд.
7. **Отложенное изменение.** Правка `riskPerTradePct` 1,0 → 1,5 с причиной → действует старое значение; в E2 меняется только после `effectiveAt`; вторая правка на той же неделе → блок.
8. **Ворота hyperopt.** В FT‑16 кнопка «Оптимизировать» заблокирована, пока шаги 1–6 `ft13_anti_liar` не закрыты; ручная галочка без вложения невозможна; после `strategy.changed` ворота переоткрываются.
9. **Sim‑часы.** В FT‑20 `advance("1w")` × 8 создаёт 8 недельных прогонов в неймспейсе тренажёра; личный виджет их не показывает; при одном вмешательстве «голова» пункт «каждое вмешательство с фактом» недоступен → итог 19/20 → кнопка микро‑лайва отсутствует.
10. **Подпись завтра.** Решение о допуске в 22:00 → кнопка неактивна до 06:00 следующего дня с обратным отсчётом.
11. **Белый список.** Ночное событие `kind: "minus_2_5_pct"` при списке [«нет связи 15 мин», «аварийная кнопка», «приказ, которого не мог отправить»] → подавлено, попало в утреннюю сводку «34 уведомления, требовали действий: 0».
12. **Локализация.** В интерфейсе нет ни одной кнопки/подписи на английском; все английские токены кликабельны и открывают русскую карточку.
13. **Персистентность.** Закрытие вкладки посреди таймера 15 минут и возврат через 10 минут → таймер показывает 5 минут остатка.
