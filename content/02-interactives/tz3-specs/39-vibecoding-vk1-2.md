# ТЗ на два интерактива трека «Вайбкодинг»

Документ для агента-реализатора. Оба интерактива — браузерные, без обращения к реальному LLM (агент-стажёр в ВК1 — детерминированный симулятор на правилах; это важно для воспроизводимости и офлайн-работы). Весь интерфейс — на русском; английский встречается только внутри кода/промптов и обязан быть кликабельным (слой «Ткни в непонятное»).

Ключевая связка, которую нужно реализовать: **артефакт, который агент-стажёр выдаёт в ВК1 «одним запросом», — это тот же файл, который ученик ревьюит в ВК2.** Один контент-кейс `case_ema_oneshot_v1` используется обоими интерактивами.

---

## 0. Общие требования к обоим интерактивам

### 0.1. Языковой слой (обязателен)
- Любой токен латиницей в коде, промпте, выводе (`shift`, `fee`, `open`, `taker`, `try/except`, `clientOrderId`, `Sharpe`, `DataFrame`, `timeout`, `bps`) — при клике/тапе показывает карточку: **русское название · одно предложение смысла · ссылка «где объяснено» (урок)**.
- Словарь один на приложение (`glossary.json`), карточки для этих двух интерактивов перечислены в приложении А. Если токена нет в словаре — он всё равно подсвечивается пунктиром и показывает «термин не описан» (чтобы ошибки словаря были видны при тестировании).
- Режим отображения кода: переключатель **«англ. / с русскими подписями»**. В режиме подписей каждая строка кода получает справа короткую русскую фразу (поле `ru` в кейсе).

### 0.2. Контент вынесен из кода
Все тексты, кейсы, формулировки додумок, таблицы симптомов — в JSON (`/content/vk1/*.json`, `/content/vk2/cases/*.json`). Компоненты не содержат хардкода строк.

### 0.3. Интеграции
- **Журнал (E5):** по завершении каждый интерактив пишет запись `{lesson, attempt, score, artifact}`. ВК1 сохраняет план ученика (markdown), ВК2 — заполненный чек-лист ревью.
- **Прогресс урока:** интерактив сообщает `mastered: true/false` по критериям освоения (ниже). Урок считается «пройденным с отработкой» только при `mastered: true` хотя бы раз.
- **Телеметрия (для метрик из плана внедрения):** события `step_sent`, `assumption_shown`, `item_marked`, `false_alarm`, `hint_used`, `attempt_finished` с полями `attempt_no`, `time_ms`. Метрика «повторные ошибки ко второй попытке −50%» считается по `assumption_shown`/`false_alarm` с одинаковым `defect_id` между попытками.

### 0.4. Устройства
Десктоп — основной. На мобильном: ВК1 работает полностью (конструктор из чипов); ВК2 — код с горизонтальной прокруткой, разметка строк через долгое нажатие, чек-лист в выезжающей панели. Не блокировать мобильных, но показывать плашку «ревью кода удобнее на широком экране».

### 0.5. Числа — только из уроков
Комиссия taker 0.05%, проскальзывание 2 bps, 500 часовых свечей BTC/USDT, EMA(9)/EMA(21), вход по open следующей свечи, «Sharpe > 5 на первом бэктесте — ошибка», «бот с look-ahead покажет +300%». Все прочие числа в интерактивах помечаются в тексте как иллюстративные.

## 1. ВК1 — тренажёр «Курьер без опыта»

### 1.1. Карточка интерактива
| Поле | Значение |
|---|---|
| Урок | ВК1 «Вайбкодинг: управляй ИИ-агентом как архитектор» |
| Тип | ТРН (тренажёр действия) + короткая ИГР-разминка |
| Целевое заблуждение | «Напиши мне бота одним запросом — и он напишет» |
| Что ученик делает руками | Дробит одну задачу на проверяемые шаги; на каждом шаге видит, что именно агент **додумает**, если шаг расплывчат; переформулирует, пока додумок не останется |
| Персонаж | Алексей (депозит 1000 $), стажёр-агент «Стажёр» (тот самый «курьер без опыта») |
| Длительность | 10–12 минут |
| Критерий освоения | План покрывает все 6 обязательных действий; 0 критичных додумок; каждый шаг проходит «ритуал пяти вопросов» |

### 1.2. Сценарий из четырёх актов

**Акт 0 · Разминка «Курьер» (60–90 сек, ИГР)**
Три раунда. На экране заказ курьеру и две формулировки, ученик выбирает одну — и видит, что курьер принёс.
1. «Купи продукты» → принёс «что-то похожее на продукты» (пакет с чипсами и лимонадом). / «Купи 2 кг картофеля в магазине на углу, чек пришли фото» → картофель + чек.
2. «Забери посылку» → принёс чужую посылку с того же пункта. / «Забери посылку №4471 на имя Алексей, паспорт покажи» → нужная посылка.
3. «Поменяй деньги» → поменял по худшему курсу в первом ларьке. / «Поменяй 100 $ в обменнике банка, курс не хуже 90, чек» → ок.
После третьего раунда — одна фраза-мостик: **«ИИ-агент — этот же курьер. Он не спросит. Он додумает. Сейчас ты это увидишь на коде бота Алексея».** Разминку можно пропустить кнопкой «Я понял, к коду».

**Акт 1 · «Одним запросом» (демонстрация заблуждения, 60 сек)**
Экран: большое поле промпта, уже заполненное:
> «Напиши бота, который скачивает часовые свечи BTC/USDT и считает доходность стратегии пересечения скользящих средних».

Единственная кнопка: **«Отправить Стажёру»**. Анимация набора кода (2–3 сек), затем результат:
- Слева — «код» (это `case_ema_oneshot_v1`, свёрнут, видны ~12 строк с многоточием).
- Справа — «Отчёт Стажёра»: **Доходность +312% · Сделок 38 · Win rate 91% · Sharpe 6,4 · Комиссии: —**.
- Кнопка **«Показать, что Стажёр додумал»** → раскрывается список из 7 карточек-додумок (см. 1.5), каждая с ценником «фантомной доходности». Внизу счётчик: **«Честный результат той же стратегии с комиссиями и без подглядывания: +4,2 % (иллюстративно)»**.
- Кнопка **«Теперь по шагам»**.

Цель акта — чтобы ученик увидел: код «запустился и показал +312 %» — и это катастрофа, а не успех.

**Акт 2 · Конструктор плана (основной тренажёр, 7–9 мин)**
Раскладка экрана (десктоп): слева — **лента шагов** (карточки сверху вниз, кнопка «+ Шаг»); по центру — **конструктор текущего шага**; справа — **ответ Стажёра** + два индикатора: «Додумок в плане: N» и «Фантомная доходность: +X %» (шкала от честных +4,2 % до +312 %).

Задача сверху экрана (не меняется): «Скрипт, который скачивает 500 часовых свечей BTC/USDT и считает доходность стратегии пересечения EMA(9)/EMA(21) с учётом комиссий. Разбей на 5–7 шагов так, чтобы каждый можно было проверить».

Механика одного шага:
1. Ученик выбирает **действие** (см. 1.3).
2. Заполняет **слоты** действия чипами (готовые варианты + слот «своё» со свободным текстом до 80 символов).
3. Отмечает галочку **«Попросить тест к этому шагу»** (или нет).
4. Нажимает **«Отправить Стажёру»**.
5. Справа появляется **ответ Стажёра**: «Понял так: …» (пересказ шага) + блок **«Додумал сам (тебя не спрашивал):»** — карточки додумок по незаполненным/расплывчатым слотам + «Результат шага» (псевдо-вывод: строки таблицы, число, «✓ работает»).
6. Ученик либо **редактирует шаг и отправляет снова**, либо **принимает** (шаг фиксируется в ленте с меткой «додумок: 0» или «додумок: N»).

Ограничения:
- Шаг с **тремя и более действиями** (ученик пытается склеить «загрузить, посчитать и построить сигнал») — Стажёр отвечает додумкой D8 «Шаг большой — сэкономил: выкинул обработку ошибок и упростил комиссии до нуля». Это реализация тезиса урока про контекстное окно.
- Максимум 8 шагов. Минимум для сдачи — 5.
- Кнопка **«Ритуал пяти вопросов»** на каждом шаге — открывает чек-лист из урока с автозаполнением: (1) шаг одной фразой? (2) формат входных данных вложен? (3) издержки указаны? (4) будущее запрещено? (5) тест попрошен? Галочки проставляются автоматически из слотов; красные пункты подсвечивают, какой слот пуст. Вопросы 3–4 «неприменимо» для шагов, где нет исполнения/расчёта результата (см. таблицу применимости в 1.3).

Подсказки: после **двух** отправок одного шага с той же додумкой появляется кнопка «Подсказать чип» — подсвечивает нужный слот (не заполняет). Использование подсказки логируется (`hint_used`), критерий освоения не ломает, но в журнал попадает «с подсказками».

### 1.3. Действия и слоты конструктора

Слоты помечены: **О** — обязательный (пустой → додумка), Р — рекомендуемый (пустой → мелкая додумка), — неприменим.

| Действие | Слоты | Обязательность |
|---|---|---|
| **Загрузить данные** | биржа/источник; пара; таймфрейм; количество свечей; «показать первые 5 строк»; «обработать ошибку сети (таймаут, повтор)» | О О О О Р Р |
| **Посчитать индикатор** | какой (EMA 9 / EMA 21 / SMA / RSI…); вход «таблица с колонкой close»; «проверить, что первые ~20 значений EMA(21) пустые» | О О Р |
| **Построить сигнал** | правило (пересечение снизу вверх / выше-ниже / своё); «использовать только свечи до момента решения»; ожидаемый выход (колонка 0/1) | О **О** Р |
| **Задать исполнение** | цена входа (open следующей свечи / close этой же / своё); цена выхода; «не использовать данные после момента решения» | **О** О **О** |
| **Учесть издержки** | комиссия taker (0,05 % / 0,1 % / своё число); проскальзывание (2 bps / своё); «на каждую смену позиции» | **О** **О** Р |
| **Посчитать метрики** | набор (доходность, max DD, число сделок, win rate); единицы (%, п.п.); сравнить с buy&hold | О Р Р |
| **Написать тест** | вид («30 искусственных свечей с известным числом сделок» / «сравнить с ручным расчётом на 5 свечах»); ожидаемый ответ (число) | О О |
| **Другое (своё)** | свободный текст | — (Стажёр отвечает додумкой D0 «Не понял слово „…“ — сделал по-своему») |

Порядок шагов свободный; проверка покрытия — по множеству, не по порядку. Но если «Посчитать метрики» отправлен **до** «Учесть издержки» и издержек нет ни в одном шаге — додумка D3 вешается на метрики.

### 1.4. Правила «додумывания» (движок Стажёра)

Детерминированный набор правил. Каждая додумка = объект:
```json
{
  "id": "D4",
  "trigger": {"action": "execution", "slot": "entry_price", "value_in": [null, "close_same"]},
  "severity": "critical",
  "title": "Взял цену входа = close той же свечи, где родился сигнал",
  "why_fake": "Сигнал считается по закрытию свечи; войти по этой цене уже нельзя — она в прошлом. Это подглядывание в будущее.",
  "phantom_pp": 280,
  "shows_in_result": "Доходность подскочила до трёхзначной. Стажёр доволен.",
  "lesson_ref": "1.7",
  "fix_hint_slot": "entry_price"
}
```

Каталог (минимум):

| ID | Триггер | Серьёзность | Что додумал Стажёр | Фантом, п.п. |
|---|---|---|---|---|
| D0 | действие «Другое» без понятного смысла | средняя | «Слово „…“ не знаю — сделал заглушку, вернул 0» | 0 |
| D1 | нет биржи/источника | средняя | «Взял первую попавшуюся биржу, у неё другой формат времени — свечи сдвинуты на 3 часа» | 0 |
| D2 | нет таймфрейма или количества | средняя | «Взял 100 дневных свечей — стратегия на 1h, но мне не сказали» | 0 |
| D3 | нигде не указана комиссия (к моменту метрик) | **критичная** | «Комиссию не назвали — поставил 0 %, так красивее» | +18 |
| D4 | цена входа не указана / close той же свечи | **критичная** | (см. JSON выше) | +280 |
| D5 | проскальзывание не указано | средняя | «Проскальзывание? Не слышал. 0» | +6 |
| D6 | загрузка без обработки ошибок | средняя | «Сеть моргнула — я молча вернул пустую таблицу; дальше всё посчиталось на нуле» | 0 (но флаг «молчаливый сбой») |
| D7 | нет ни одного шага «Написать тест» в плане | **критичная** | «Тестов не просили. Я написал: „Всё работает ✓“» | +4 (символически: «уверенность без проверки») |
| D8 | ≥3 действий в одном шаге | **критичная** | «Шаг большой — сэкономил: выкинул обработку ошибок, комиссии упростил, тест не писал» | суммарно D3+D6 |
| D9 | метрики без единиц | мелкая | «Проскальзывание указал в процентах, комиссию в долях, доходность в разах — пусть читатель разбирается» | 0 |
| D10 | индикатор без проверки «первые значения пустые» | мелкая | «EMA(21) считаю с первой свечи — первые 20 значений выдуманы, сигналы там ложные» | +2 |
| D11 | сигнал без запрета на будущее | **критичная** | «Для сглаживания взял окно по центру (center=True): каждая точка знает будущее» | +40 |

Правила агрегации:
- Фантом складывается по уникальным ID, не по числу отправок.
- «Показанная доходность» = 4,2 % + сумма фантомов принятых шагов (D4 и D11 не суммируются — берётся максимум; оба про подглядывание).
- **Критичные додумки блокируют кнопку «Принять шаг»** до исправления? — **Нет.** Ученик может принять шаг с додумкой (так он увидит последствия в Акте 3), но кнопка «Принять» становится жёлтой с текстом «Принять с додумками (N)». Мастерство при этом не засчитывается.

Ответ Стажёра всегда содержит фразу-напоминание (ротируется): «Я не спрашиваю — я додумываю», «Спросить мог бы, но так не умею», «Я запустился, значит всё хорошо, правда?».

### 1.5. Семь додумок Акта 1 (фиксированный список)
Это D1, D3, D4, D5, D6, D7, D9 — именно они посеяны в коде `case_ema_oneshot_v1` (см. раздел 2.8), чтобы в ВК2 ученик нашёл те же дыры уже в коде.

### 1.6. Оценивание
```
coverage  = |{загрузить, индикатор, сигнал, исполнение, издержки, метрики} ∩ действия_плана| / 6
tests     = есть ≥1 шаг «Написать тест»
critical  = число уникальных критичных додумок в принятых шагах
granular  = все шаги ≤ 2 действий
mastered  = coverage == 1 && tests && critical == 0 && granular
```
Шкала для экрана результата: «Архитектор» (mastered), «Почти архитектор» (критичных 1–2 или нет теста), «Заклинатель промптов» (coverage < 0,8 или ≥3 критичных).

### 1.7. Тексты обратной связи (ключевые)
- При первой додумке D4: «Обрати внимание: Стажёр не ошибся — он **выбрал** удобное. Так делает любой агент, когда слот пустой. Твоя работа — не оставлять пустых слотов».
- При принятии шага с критичной додумкой: «Ты принял шаг, где Стажёр решил за тебя. В Акте 3 увидишь, во сколько это обошлось».
- Вердикт «Архитектор»: «Ни одной додумки. Заметь: ты не написал ни строчки кода — ты написал ТЗ. Это и есть вайбкодинг».
- Вердикт «Заклинатель»: «Твой план — тот же „напиши бота“, только в N частях. Вернись к шагу с самой дорогой додумкой (подсвечен)».

### 1.8. Что НЕ делать
- Не подключать LLM для оценки свободного текста в MVP — только слоты + словарь синонимов для слота «своё» (см. Приложение Б).
- Не показывать «правильный план» до завершения попытки; после — показывать эталон из ВК4 (6 шагов) с пометкой «один из хороших вариантов».
- Не наказывать за порядок шагов.
- Не давать таймер.

### 1.9. Данные/контракт компонента
```ts
type Action = 'load'|'indicator'|'signal'|'execution'|'costs'|'metrics'|'test'|'other';
type Step = { id: string; action: Action; slots: Record<string, string|null>; askTest: boolean; freeText?: string;
              submissions: number; assumptions: string[]; accepted: boolean };
type Vk1State = { act: 0|1|2|3; steps: Step[]; hintsUsed: number; startedAt: number };
type Vk1Result = { coverage: number; critical: number; tests: boolean; granular: boolean;
                   mastered: boolean; shownReturn: number; phantomPp: number; planMd: string };
```

### 1.10. Приёмочные критерии

Обратная связь мягкая: «Хорошая гипотеза — теперь проверим кодом», подозрения сохраняются как предзаполненные фокусы в чек-листе. Это отработка тезиса «сначала диагноз, потом детали».

### 2.4. Основной экран Уровня 2 (движок E6)
Раскладка: слева **код с номерами строк** (60–70 строк, моноширинный, режим «англ./с русскими подписями»); справа **панель чек-листа** из 7 пунктов.

Механика разметки (проверено на новичках — от чек-листа к коду, а не наоборот):
1. Ученик нажимает пункт чек-листа → он становится **активным** (подсвечен).
2. Кликает по строкам кода, которые относятся к этому пункту (можно несколько; повторный клик снимает). Строка получает цветной маркер пункта. Одна строка может нести маркеры нескольких пунктов.
3. Либо нажимает у пункта кнопку **«Чисто»** (тогда маркеры этого пункта снимаются).
4. У каждого пункта — раскрывашка **«Что искать»**: 2–3 подсказки-ориентира из урока без указания строк (например, для п. 2: «ищи слова fee / commission / slippage; нет их или нули — бэктест фальшивый»). Использование подсказки не штрафуется, логируется.
5. Кнопка **«Сдать ревью»** активна, когда каждый из 7 пунктов имеет вердикт (маркеры или «чисто»).

После сдачи — **разбор по пунктам** (аккордеон): для каждого пункта статус ✅ найден / ⚠️ найден, но не в тех строках / ❌ пропущен / 🚨 ложная тревога (сказал «дефект», а там чисто) — и объяснение: где на самом деле, почему это смертельно, ссылка на урок. Правильные строки подсвечиваются в коде.

Правило зачёта строки: совпадение хотя бы с одной строкой из `defect.lines` **±1 строка**. Для «чисто» — пункт в `clean_items`.

Ложная тревога = пункт помечен как дефект, а в кейсе он в `clean_items`. **Это обязательный элемент:** на Уровне 2 в каждом варианте кейса 1–2 пункта чистые; иначе ученик научится «отмечать всё».

### 2.5. Таблица «симптом → диагноз» (контент)
Показывается на этапе гипотезы как справка и в разборе. Первые пять строк — из урока, две добавлены.

| Что видишь в коде/результате | Вероятный диагноз | Пункт чек-листа |
|---|---|---|
| Equity растёт идеально плавно, без просадок | Look-ahead или нулевые издержки | 1, 2 |
| Вход по той же цене, что и сигнальная свеча close | Look-ahead bias | 1 |
| Ни одного слова fee/commission в файле | Бэктест без издержек — результат мнимый | 2 |
| `requests.post(...)` без try/except и таймаута | Первый сбой сети = зависший или дублирующий бот | 3, 4 |
| Sharpe > 5 на первом же бэктесте | Ошибка в данных или коде, а не «грааль» | 1, 2 |
| Число сделок 7 при 500 свечах, доходность +90 % | Мало данных: результат — 2–3 удачных сделки (М30) | — (не дефект кода, а выборки) |
| Win rate 100 % на 30+ сделках | Look-ahead или нет стопа (мартингейл, П24) | 1 |

Последние две строки специально не привязаны к «дефекту кода» — это тренировка различать «баг» и «шум выборки».

### 2.6. Семь пунктов чек-листа (канонические формулировки для UI)
1. **Подглядывание в будущее (look-ahead).** Сигнал по свече N исполняется по цене свечи N. Верно: вход по open[N+1].
2. **Издержки.** Нет комиссии/проскальзывания или они нули. Минимум: taker 0,05 % на сделку + проскальзывание.
3. **Ошибки API.** Нет try/except, таймаута, повтора с паузой, реакции на 429. Молчаливая ошибка = бот думает, что ордер есть.
4. **Идемпотентность ордеров.** Повтор после таймаута создаёт вторую позицию (нет clientOrderId).
5. **Единицы измерения.** bps ↔ %, секунды ↔ миллисекунды, базовая ↔ котируемая валюта. Не падает — тихо искажает.
6. **Деление на ноль и пустые данные.** Пустой список сделок, пропуски свечей, нулевой объём.
7. **Состояние при перезапуске.** Бот забывает открытую позицию вместо восстановления по данным биржи.

### 2.8. Эталонный кейс `case_ema_oneshot_v1` (полный код с посевом)

Код должен быть **логически цельным** (запускаемым при наличии API), 55–60 строк, с русскими комментариями там, где это естественно для «кода от агента». Ниже — референс; агент-реализатор вносит его в JSON вместе с полем `ru` (русские подписи перечислены после кода).

```python
 1  import time
 2  import requests
 3  import pandas as pd
 4  import numpy as np
 5
 6  URL = "https://api.exchange.example/klines"
 7
 8  def load_candles(symbol="BTCUSDT", tf="1h", limit=500):
 9      r = requests.get(URL, params={"symbol": symbol, "interval": tf, "limit": limit})
10      data = r.json()
11      df = pd.DataFrame(data, columns=["ts", "open", "high", "low", "close", "volume"])
12      return df
13
14  def add_indicators(df):
15      df["ema_fast"] = df["close"].ewm(span=9).mean()
16      df["ema_slow"] = df["close"].ewm(span=21).mean()
17      return df
18
19  def make_signals(df):
20      up = (df["ema_fast"] > df["ema_slow"]) & (df["ema_fast"].shift(1) <= df["ema_slow"].shift(1))
21      dn = (df["ema_fast"] < df["ema_slow"]) & (df["ema_fast"].shift(1) >= df["ema_slow"].shift(1))
22      df["enter"] = up.astype(int)
23      df["exit"] = dn.astype(int)
24      return df
25
26  FEE = 0.0          # комиссия биржи
27  SLIPPAGE = 2       # проскальзывание
28
29  def backtest(df):
30      position = None
31      trades = []
32      for i in range(len(df)):
33          price = df["close"].iloc[i]
34          if df["enter"].iloc[i] == 1 and position is None:
35              position = price * (1 + SLIPPAGE)
36          elif df["exit"].iloc[i] == 1 and position is not None:
37              pnl = (price - position) / position - FEE * 2
38              trades.append(pnl)
39              position = None
40      return trades
41
42  def report(trades):
43      wins = [t for t in trades if t > 0]
44      win_rate = len(wins) / len(trades)
45      total = np.prod([1 + t for t in trades]) - 1
46      print(f"Сделок: {len(trades)}  win rate: {win_rate:.0%}  доходность: {total:.1%}")
47
48  def send_order(side, qty):
49      for attempt in range(3):
50          try:
51              resp = requests.post(URL + "/order", json={"side": side, "qty": qty}, timeout=5)
52              return resp.json()
53          except Exception:
54              continue
55
56  def run_live():
57      position = None     # при старте считаем, что позиции нет
58      while True:
59          df = make_signals(add_indicators(load_candles()))
60          if df["enter"].iloc[-1] == 1 and position is None:
61              send_order("buy", 0.01); position = "long"
62          elif df["exit"].iloc[-1] == 1 and position == "long":
63              send_order("sell", 0.01); position = None
64          time.sleep(3600)
65
66  trades = backtest(make_signals(add_indicators(load_candles())))
67  report(trades)
```

|---|---|---|---|---|
| 1 | 33, 34–35, 36–37 (**33**) | `price = close[i]` и для сигнала, и для исполнения | `price = df["open"].iloc[i+1]` при `i+1 < len(df)` | строка 33 → `price = df["open"].iloc[i+1] if i+1 < len(df) else None` + проверка `None` |
| 2 | **26** (и 37 как следствие) | `FEE = 0.0` | `FEE = 0.0005` (taker 0,05 %) | `FEE = 0.0005` |
| 3 | **9**, 10 | `requests.get` без `timeout`, без `try/except`, без проверки статуса/429 | `try: r = requests.get(..., timeout=10); r.raise_for_status() except ...: пауза и повтор` | строки 9–10 с `timeout=10`, `raise_for_status()` и `try/except` с `time.sleep(2)` |

### 2.9. Уровень 3 «Просветный тест» (лог решений)
Показывается таблица из 12 строк лога, сгенерированного «после того как попросили агента логировать каждое решение»:

| # | Время решения | Свеча сигнала | Время цены исполнения | Цена | Сигнал |
|---|---|---|---|---|---|
| 1 | 10:00 (close 09:00–10:00) | 09:00 | 10:00 open следующей | 65 120 | вход |
| … | … | … | … | … | … |

Посеяны 3 строки, где «время цены исполнения» **равно или раньше** времени решения (например, решение 14:00, цена — close свечи 13:00–14:00 в 14:00; или цена в 13:30). Ученик отмечает подозрительные строки. Правило: строка ловится, если `exec_time <= decision_time`. Обратная связь: «Время решения всегда должно быть раньше времени цены исполнения. Здесь — нет: это look-ahead, который виден без чтения кода».

Мини-ловушка: одна строка с исполнением через 3 часа после решения (лимитный ордер долго висел) — это **не** дефект; отметка на ней = ложная тревога с пояснением про `unfilledtimeout` (FT-06).

### 2.10. Уровень 4 «Почини по одному» (опционально)
Для каждого найденного дефекта — три варианта правки (`fixes` из кейса), ровно один верный. Одна из неверных всегда «правдоподобно хуже» (например, `shift(-1)`). После выбора показывается диф двух строк. Правило урока «одна правка = один запрос» — в интерфейсе правки применяются по одной, с кнопкой «Следующий дефект». Итог — «чистая» версия кода и пересчитанный псевдо-отчёт: **+4,2 %, 38 сделок, win rate 47 %, комиссии учтены** — та же честная цифра, что в ВК1.

### 2.11. Git-минимум как микро-элемент

### 2.12. Оценивание Уровня 2
```
verdict_ok(item) = (item ∈ defects && ∃ marked ∈ lines±1) || (item ∈ clean_items && marked == 'clean')
false_alarm(item) = item ∈ clean_items && marked != 'clean'
missed(item) = item ∈ defects && marked == 'clean'
near_miss(item) = item ∈ defects && marked строки, но ни одна не в lines±1

score = Σ verdict_ok / 7
mastered = Σ verdict_ok ≥ 6 && Σ false_alarm ≤ 1
```
Near-miss даёт 0,5 балла и отдельное объяснение «Пункт угадан, место — нет: смотри строку N».

Повторная попытка — другой вариант посева (`variants`) и, при наличии, другой кейс из банка. Банк: минимум 3 кейса на Уровень 2 — `case_ema_oneshot_v1` (этот), `case_rsi_dip_v1` (RSI < 30 + `bfill()` пропусков как дефект п.1, комиссия задана как `0.05` вместо `0.0005` — п.5), `case_breakout_v1` (пробой максимума с `rolling(center=True)` — п.1; `time.sleep(500)` вместо секунд — п.5; ордер в `amount` котируемой валюты — п.5). Для каждого — те же 7 пунктов, свои `clean_items`.
