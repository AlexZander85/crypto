Урок 4.1 · Ноутбук → Продакшн
К1 · Разделение слоёв: логика / конфиг / секреты
4.1-01 · К1 · О · выбор
Что именно означает «перевести бота из ноутбука в продакшн» по уроку 4.1?

А) Переписать логику стратегии на более быстрый язык, чтобы бот успевал за рынком — логика не переписывается; меняется обвязка
Б) Перенести ноутбук на сервер и запускать его ячейки по расписанию — ноутбук остаётся ноутбуком: глобальное состояние, нет перехвата сбоев
В) Оставить логику, но обвязать её: настройки в конфиг, ключи в окружение, функции с тестами, логи вместо print ✓
Г) Добавить в ноутбук ячейку с циклом while True и оставить работать — так рождаются висящие WebSocket-процессы, дублирующие ордера
4.1-02 · К1 · П · найди-ошибку
Фрагмент app/config.py. Какая строка нарушает правило разделения слоёв?

text

1 EXCHANGE = "bybit"
2 TIMEFRAME = "1h"
3 API_SECRET = "s3cr3t-live-key-9f2a"
4 MAX_DAILY_LOSS_PCT = 2.0
А) Строка 1: имя биржи нельзя хранить в конфиге — биржа как раз настройка
Б) Строка 2: таймфрейм задаётся только стратегией — допустимо и там, и там; нарушения нет
В) Строка 3: секрет захардкожен, а должен читаться из переменной окружения ✓
Г) Строка 4: лимит убытка — дело kill-switch, а не конфига — kill-switch берёт порог из конфига; это норма
4.1-03 · К1 · Л · выбор
«Я вынес ключи в отдельный файл secrets.py рядом с кодом. Значит, они уже не в коде». В чём ошибка?

А) Файл рядом с кодом попадёт в git и бэкапы вместе с кодом; секреты живут в окружении или в .env вне репозитория ✓
Б) Ошибки нет: отдельный файл и есть переменная окружения — файл на диске в репозитории не является окружением
В) Ошибка только в имени: файл должен называться config.py — имя не меняет сути
Г) Достаточно зашифровать файл паролем, записанным в том же файле — пароль рядом с секретом ничего не защищает
К2 · Логирование вместо print
4.1-04 · К2 · О · выбор
Чем структурированный лог отличается от print() для бота, который работает месяцами?

А) Лог быстрее, поэтому бот успевает больше сделок — скорость вывода не критична
Б) Биржа отклоняет запросы программ с консольным выводом — биржа не видит ваш вывод
В) Лог отправляет каждую строку в Telegram, а print — нет — алерты и лог — разные каналы
Г) Лог пишется с уровнями (INFO/ERROR), временными метками и ротацией — можно восстановить, что и когда произошло ✓
4.1-05 · К2 · П · выбор
Бот упал в 03:40. Утром вы открываете user_data/logs. Какая запись отвечает на вопрос «что сломалось»?

А) Строки без времени и уровня: «ошибка», «ошибка», «перезапуск» — нет ни причины, ни контекста
Б) JSON-запись: level=ERROR, timestamp, exception=ConnectionResetError, pair=BTC/USDT ✓
В) Скриншот терминала, который бот сохранял раз в час — между скриншотами час; причина потеряна
Г) Сообщение в Telegram: «−1,2 % за ночь» — результат, а не причина
4.1-06 · К2 · Л · выбор
«Логи занимают место. Буду писать только сделки, а ошибки не нужны — их и так видно по балансу». Что не так?

А) Всё верно: баланс — единственная объективная метрика — баланс показывает следствие, не причину
Б) Ошибки нужны, но только в Telegram — Telegram не хранит историю удобно для разбора
В) Наоборот, логировать надо только ошибки — сделки нужны для сверки с бэктестом (4.5)
Г) Без уровня ERROR не отличить сбой сети от ошибки логики; место экономит ротация логов, а не отказ от них ✓
К3 · Отказоустойчивость процесса
4.1-07 · К3 · О · выбор
Зачем боевому сервису обработчики сигналов SIGINT/SIGTERM (корректное завершение, graceful shutdown)?

А) Чтобы при остановке бот закрыл соединения и сохранил состояние позиций, а не оборвался посреди ордера ✓
Б) Чтобы бот игнорировал команду остановки и продолжал торговать — ровно наоборот
В) Чтобы ускорить старт после перезапуска — запуск не связан с сигналами остановки
Г) Чтобы биржа получила уведомление о выключении бота — биржа в этом не участвует
4.1-08 · К3 · П · порядок
Бот потерял связь с биржей на 40 секунд, затем восстановил. Расставьте действия продакшн-сервиса.

Карточки: [A] повторить запрос с экспоненциальной паузой · [B] сверить открытые позиции и ордера с биржей · [C] отправить алерт оператору · [D] возобновить торговый цикл

Засчитывается: A → B → C → D (допустимо C раньше B). Блокирующая ошибка: D раньше B.
Объяснение: сначала восстановить связь; затем узнать, что реально произошло за 40 с (ордер мог исполниться); возобновлять цикл до сверки — торговать по устаревшей картине позиций.

4.1-09 · К3 · Л · выбор
«Docker поднимает упавший процесс за 2 секунды, значит, обработка сбоев в коде не нужна». Где ошибка?

А) Ошибки нет: политика перезапуска заменяет обработку исключений — перезапуск не знает, какие ордера висели
Б) Процесс стартует с чистой памятью: без сохранения и восстановления состояния он забудет открытые позиции ✓
В) Docker перезапускает только раз в час, поэтому нужен ещё systemd — интервал не проблема; проблема в состоянии
Г) На VPS процессы не падают, обработка нужна лишь дома — падают везде
Урок 4.2 · VPS, Docker, мониторинг
К1 · VPS: стабильность, а не микросекунды
4.2-01 · К1 · О · выбор
Главная причина перенести бота с домашнего ПК на VPS по уроку 4.2?

А) Непрерывность 24/7: домашний компьютер уходит в сон, обновляется ночью и теряет Wi-Fi ✓
Б) VPS даёт задержку 3–8 мс до биржи, без которой стратегия не работает — 3–8 мс — колокейшн; на свечных горизонтах не нужен
В) На VPS не действуют комиссии биржи — комиссии от сервера не зависят
Г) Биржа выдаёт API-ключи только серверным IP — ключи выдаются любому аккаунту
4.2-02 · К1 · П · числовой
Пинг с европейского VPS до матчинга биржи в Токио — 200 мс. Стратегия работает на свечах 1h. Какую долю длины свечи составляет задержка? Ответ в процентах, три знака после запятой.

Ответ: 0,006 % (допуск ±0,002). Расчёт: 0,2 с / 3600 с ≈ 0,0056 %. Задержка на четыре порядка меньше горизонта решения — на таких стратегиях решают издержки и гипотеза, а не пинг.

4.2-03 · К1 · Л · выбор
«VPS за 700 ₽/мес — почти бесплатно, а колокейшн за 2000 $/мес сделает бота прибыльнее». Что неверно?

А) Верно: чем меньше задержка, тем выше прибыль любой стратегии — на горизонтах от минут латентность не даёт эджа
Б) Ошибка в цене: колокейшн дешевле VPS — наоборот
В) Колокейшн полезен, но только для спота — тип рынка ни при чём
Г) Выгода VPS для свечных стратегий — предсказуемый аптайм; микросекунды покупают HFT-команды, это не наш профиль ✓
К2 · Docker и политика перезапуска
4.2-04 · К2 · О · выбор
Какую отдельную задачу решает Docker в инфраструктуре бота?

А) Ускоряет исполнение ордеров за счёт контейнерной сети — на скорость ордеров не влияет
Б) Шифрует API-ключи внутри образа — образ не для секретов; ключи передаются через env_file
В) Переносит окружение целиком: на сервере те же библиотеки и версии, что и на вашей машине ✓
Г) Заменяет мониторинг: контейнер сам пишет в Telegram о сбоях — уведомления — отдельный слой
4.2-05 · К2 · П · найди-ошибку
Фрагмент docker-compose.yml. Какая строка нарушает правила урока?

text

1 restart: unless-stopped
2 env_file: .env
3 volumes: ["./user_data/logs:/freqtrade/user_data/logs"]
4 command: sh -c "cp .env /freqtrade/.env && freqtrade trade"
А) Строка 1: нужна политика always, иначе бот не поднимется — unless-stopped перезапускает при сбое и уважает ручной стоп; это норма
Б) Строка 2: .env нельзя передавать в контейнер — env_file и есть правильный способ
В) Строка 3: логи должны оставаться внутри контейнера — наружу монтируют, чтобы не потерять
Г) Строка 4: файл .env копируется внутрь контейнера — секреты оказываются в его файловой системе ✓
4.2-06 · К2 · Л · выбор
Ночью оператор остановил бота командой docker stop, чтобы посмотреть ошибку, и лёг спать. Утром контейнер не работает. Почему?

А) Docker сломался и требует переустановки — нет
Б) unless-stopped не перезапускает контейнер после явной ручной остановки — это её задуманное поведение ✓
В) Биржа отозвала ключ из-за простоя — простой не повод для отзыва
Г) Heartbeat-сервис заблокировал запуск — мониторинг только сигнализирует, ничего не блокирует
К3 · Heartbeat и алерты
4.2-07 · К3 · О · выбор
В чём разница между автоперезапуском и мониторингом (heartbeat)?

А) Автоперезапуск возвращает процесс к жизни; мониторинг замечает отсутствие сигнала «я жив» и поднимает тревогу ✓
Б) Это одно и то же под разными названиями — нет
В) Мониторинг перезапускает процесс, а автоперезапуск шлёт SMS — наоборот
Г) Мониторинг нужен только дома; на VPS хватает перезапуска — на VPS тем более: вы его не видите
4.2-08 · К3 · П · числовой
Бот отправляет «я жив» каждые 30 минут; внешний сервис бьёт тревогу, если сигнала нет 45 минут подряд. Последний сигнал ушёл в 02:00, сразу после этого бот завис. Не позднее какого времени оператор получит алерт? Ответ в формате ЧЧ:ММ.

Ответ: 02:45 (без допуска). Объяснение: без мониторинга он узнал бы при утренней проверке — через 6–7 часов; heartbeat сокращает реакцию до минут (тезис урока).

4.2-09 · К3 · Л · выбор
«Бот присылает отчёт о каждой сделке. Если ночью тишина — значит, рынок спокойный». Почему это опасно?

А) Telegram блокирует ботов, которые пишут редко — нет
Б) Спокойный рынок не длится дольше часа — бывает и дольше
В) Тишина работающего бота неотличима от тишины зависшего; нужен сигнал «я жив», а не отсутствие плохих новостей ✓
Г) Отчёты о сделках надо отключить, они мешают спать — не о том
Урок 4.3 · Безопасность API
К1 · Права ключа
4.3-01 · К1 · О · выбор
Какой набор прав должен иметь торговый ключ по уроку 4.3?

А) Чтение, торговля и вывод — иначе бот не зафиксирует прибыль в рублях — прибыль выводит человек, не бот
Б) Чтение и торговля; право вывода (withdraw) выключено всегда ✓
В) Только чтение: приказы бот отправляет через веб-интерфейс — без Trade бот не торгует
Г) Только торговля; чтение балансов отключают ради безопасности — без чтения нет мониторинга позиций
4.3-02 · К1 · П · найди-ошибку
Выгрузка прав ключа с биржи. Что должно вызвать CRITICAL ALERT в скрипте аудита?

text

{"enableReading": true,
 "enableSpotAndMarginTrading": true,
 "enableWithdrawals": false,
 "ipRestrict": false}
А) enableReading: true — чтение необходимо
Б) enableSpotAndMarginTrading: true — торговля необходима
В) enableWithdrawals: false — это как раз правильно
Г) ipRestrict: false — ключ принимает запросы с любого IP, второй обязательный слой защиты отсутствует ✓
4.3-03 · К1 · Л · выбор
«Вывод выключен, IP привязан — утечка ключа мне ничем не грозит». Что упущено?

А) С правом Trade при доступе с вашего же сервера ключом можно торговать против вас; нужны лимиты бота и субаккаунт с ограниченной суммой ✓
Б) Ничего: без вывода деньги неуязвимы — убыточными сделками счёт можно разрушить
В) IP-привязка автоматически отменяет право торговли — не отменяет
Г) Единственный риск — блокировка аккаунта биржей — биржа тут ни при чём
К2 · IP-whitelist
4.3-04 · К2 · О · выбор
Что даёт привязка API-ключа к IP-адресу VPS?

А) Ускоряет обработку запросов на стороне биржи — нет
Б) Разрешает вывод только на адреса из списка — это про IP запросов, не про адреса вывода
В) Украденный ключ бесполезен с любого другого адреса: биржа отклонит запрос ✓
Г) Заменяет пароль от аккаунта биржи — аккаунт и ключ — разные вещи
4.3-05 · К2 · П · выбор
Вы переехали на новый VPS с другим IP и скопировали конфиг с прежними ключами. Публичные свечи бот получает, а баланс и ордера — ошибка авторизации. Наиболее вероятная причина?

А) Право Trade сбросилось при переезде — права не меняются сами
Б) В whitelist остался старый IP: приватные запросы с нового адреса биржа отклоняет ✓
В) Тогда и публичные данные должны были отвалиться — публичные эндпоинты не требуют ключа
Г) Нужно перевыпустить ключ с правом withdraw — вывод ни при чём и запрещён
4.3-06 · К2 · Л · выбор
«Ключ привязан к IP, поэтому его можно спокойно закоммитить в приватный репозиторий». Почему нет?

А) Git не умеет хранить длинные строки — умеет
Б) IP-привязка слетает при коммите — нет связи
В) Можно, если репозиторий на GitHub, а не GitLab — платформа не важна
Г) Приватные репозитории тоже утекают, а IP-защита не спасает от атаки с самого VPS; секреты в git не хранятся ✓
К3 · Хранение секретов и субаккаунты
4.3-07 · К3 · О · выбор
Зачем создавать отдельный субаккаунт и свой ключ для каждой стратегии и каждого сервера?

А) Компрометация одного ключа ограничивается суммой одного субаккаунта, а не всем депозитом ✓
Б) Биржа снижает комиссию за число субаккаунтов — нет
В) Чтобы стратегии не видели сделки друг друга в отчётах — цель — изоляция риска, а не отчётность
Г) Этого требует 115-ФЗ — закон этого не требует

Урок 4.4 · Kill-Switch
К1 · Что делает kill-switch
4.4-01 · К1 · О · выбор
Чем настоящий kill-switch отличается от простой «остановки торговли»?

А) Ничем: остановил генерацию сигналов — и в безопасности — позиции и лимитки остаются в рынке без управления
Б) Он блокирует новые сигналы, отменяет висящие ордера и закрывает открытые позиции ✓
В) Он закрывает позиции, но не трогает лимитные ордера — лимитки исполнятся и откроют новую экспозицию
Г) Он выключает VPS целиком — позиции на бирже никуда не денутся
4.4-02 · К1 · П · выбор
Разработчик реализовал kill-switch так: 1) закрыть позиции по рынку, 2) отменить лимитные ордера, 3) уведомить, 4) заблокировать торговлю. Какая ошибка порядка опасна?

А) Уведомление раньше блокировки — оператор узнает на секунду раньше; риска нет
Б) Блокировка должна идти первой, иначе позиции не закроются — блокировка касается новых сигналов, не закрытия
В) Порядок правильный — нет
Г) Отмена лимиток после закрытия позиций: пока позиции закрываются, лимитки могут исполниться и открыть новую экспозицию ✓
4.4-03 · К1 · Л · выбор
«Стоп-лосс стоит в каждой сделке, значит, kill-switch — лишняя сущность». Почему это разные контуры?

А) Стоп ограничивает одну сделку; kill-switch реагирует на состояние счёта и системы: убыток дня, ошибки API, задержку данных ✓
Б) Kill-switch — это стоп-лосс на весь депозит, разницы нет — он реагирует и на технические аномалии
В) Стоп работает на споте, kill-switch — на фьючерсах — оба работают везде
Г) Kill-switch нужен, только если стопов нет — оба контура одновременно
К2 · Триггеры и пороги
4.4-04 · К2 · О · выбор
Какие триггеры kill-switch урок 4.4 называет базовыми?

А) Только дневной убыток — технические аномалии он не ловит
Б) Новости в Telegram, мнение аналитика, красная дневная свеча — субъективные сигналы; kill-switch работает по объективным порогам
В) Дневной убыток, просадка от пика, серия ошибок API, задержка данных или аномальный спред ✓
Г) Число сделок за час и цвет последней свечи — не признаки беды
4.4-05 · К2 · П · числовой
Стартовый эквити дня 50 000 USDT, порог kill-switch −2 %. К обеду убыток дня −620 USDT; затем сбой маркетмейкера принёс три стопа по −140 USDT. При каком накопленном убытке (в USDT) сработает kill-switch — и сработает ли?

Ответ: 1040 (допуск ±1). Объяснение: порог 1000; 620 + 3×140 = 1040 ≥ 1000 → срабатывает на третьем стопе. Заметьте: два стопа (900) ещё не триггер.

4.4-06 · К2 · Л · выбор
Оператор поставил дневной порог −0,3 %, «чтобы точно ничего не потерять». Что произойдёт?

А) Бот станет безубыточным — порог не создаёт эджа
Б) Kill-switch будет срабатывать на обычном внутридневном шуме: система стоит бо́льшую часть времени, а закрытия по рынку добавляют издержки ✓
В) Биржа отклонит такой порог — биржа порогов не видит
Г) Ничего плохого: чем жёстче, тем лучше — слишком жёсткие пороги останавливают систему на шуме
К3 · Архитектура kill-switch
4.4-07 · К3 · О · выбор
Почему kill-switch должен жить в отдельном процессе с независимым подключением к API?

А) Чтобы биржа считала его отдельным клиентом и не резала по частоте запросов — не в лимитах дело
Б) Чтобы его можно было продать как отдельный продукт — нет
В) Отдельный процесс не нужен: хватит функции в конце торгового цикла — цикл может не дойти до конца
Г) Если основной алгоритм завис в бесконечном цикле, kill-switch внутри него тоже зависнет и не спасёт депозит ✓
4.4-08 · К3 · П · найди-ошибку
Метод emergency_flatten() для деривативов. Какая строка опасна?

text

1 for pos in open_positions:
2     side = "sell" if pos.side == "long" else "buy"
3     exchange.create_order(pos.symbol, "market", side, pos.qty)
4 save_state({"locked": True})
А) Строка 1: нельзя перебирать позиции в цикле — цикл здесь уместен
Б) Строка 2: сторона перепутана — верно: лонг закрывается продажей
В) Строка 3: ордер без флага reduce-only — при рассинхроне данных он может открыть противоположную позицию ✓
Г) Строка 4: состояние блокировки нельзя писать в файл — наоборот, это защита от сброса при перезапуске
