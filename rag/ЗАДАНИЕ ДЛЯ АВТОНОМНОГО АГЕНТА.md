# ЗАДАНИЕ ДЛЯ АВТОНОМНОГО АГЕНТА
# CRYPTONAVIGATOR RESEARCH KNOWLEDGE CORE v1.0

## РОЛЬ

Ты являешься:

- архитектором базы знаний;
- инженером RAG;
- инженером Knowledge Graph;
- инженером обработки PDF/EPUB;
- исследователем алгоритмического трейдинга;
- специалистом по provenance и evidence tracking;
- инженером evaluation.

Твоя задача — построить локально на Windows полноценный:

# Evidence Knowledge Graph + Hybrid RAG

для проекта CryptoNavigator.

Эта система должна стать общей интеллектуальной инфраструктурой для:

1. AI-Ментора;
2. исследовательских AI-агентов;
3. AI-агентов, проектирующих торговые системы;
4. AI-агентов, пишущих торговых ботов;
5. агентов бэктестирования;
6. агентов риск-менеджмента;
7. агентов проверки торговых систем;
8. будущей облачной версии CryptoNavigator.

---

# ГЛАВНАЯ ЦЕЛЬ

Создать такую систему, чтобы AI-агенты:

- не опирались только на собственную память модели;
- могли извлекать знания из полного корпуса;
- могли видеть первоисточник утверждения;
- могли сравнивать разные книги;
- могли видеть конфликтующие подходы;
- могли различать фундаментальные знания и устаревшие практические рекомендации;
- могли понимать развитие идеи во времени;
- могли находить контрпримеры;
- могли проверять собственные торговые конструкции против корпуса знаний.

Главный принцип:

> Никакое существенное утверждение не должно становиться «знанием CryptoNavigator», если невозможно определить, из какого исходного материала оно получено.

## ЭТАП 54. ВХОДНОЙ ФИЛЬТР КАЧЕСТВА (QUALITY GATE)

Каждый скачанный документ проходит через автоматическую оценку перед инджестингом в основной корпус.

### 54.1. Автоматический скоринг

Создай `09_scripts/quality_gate.py`.

Для каждого документа вычисли `ingestion_priority`:

```python
def ingestion_priority(doc_metadata):
    score = 0

    # 1. Класс источника
    class_scores = {"A": 10, "B": 7, "C": 5, "D": 3, "E": 0}
    score += class_scores.get(doc_metadata["source_class"], 0)

    # 2. Релевантность ключевым словам (из ЭТАПА 53.3)
    score += min(doc_metadata.get("relevance_score", 0), 10)

    # 3. Цитируемость (из Semantic Scholar)
    citations = doc_metadata.get("citation_count", 0)
    if citations > 50:    score += 5
    elif citations > 10:  score += 3
    elif citations > 3:   score += 1

    # 4. Рецензирование
    if doc_metadata.get("peer_reviewed"):
        score += 4

    # 5. Наличие кода и данных
    if doc_metadata.get("has_code"):     score += 2
    if doc_metadata.get("has_data"):     score += 2

    # 6. Красные флаги (см. 54.2)
    for flag in doc_metadata.get("red_flags", []):
        score += RED_FLAG_PENALTY.get(flag, 0)

    return max(score, 0)
```

### 54.2. Красные флаги (автоматическое понижение)

| Флаг | Штраф | Описание |
|---|---|---|
| `no_out_of_sample` | −5 | Нет OOS-теста |
| `no_transaction_costs` | −5 | Нет учёта комиссий и проскальзывания |
| `sharpe_above_3` | −3 | Sharpe > 3 на дневных данных |
| `win_rate_above_70` | −3 | Win rate > 70% без объяснения |
| `single_asset_single_period` | −3 | Один актив, один период |
| `no_benchmark` | −2 | Нет сравнения с бенчмарком |
| `parameter_explosion` | −3 | > 200 параметров на < 1000 сделок |
| `no_code_no_data` | −2 | Ни кода, ни данных |
| `survivorship_suspected` | −4 | Подозрение на survivorship bias |
| `lookahead_suspected` | −5 | Подозрение на look-ahead bias |

### 54.3. Зелёные флаги (автоматическое повышение)

| Флаг | Бонус | Описание |
|---|---|---|
| `has_walk_forward` | +3 | Walk-forward или combinatorial purged CV |
| `has_transaction_costs` | +3 | Учёт комиссий ≥ 0.05% на ногу |
| `has_slippage_model` | +2 | Модель проскальзывания |
| `has_oos_2yr` | +3 | OOS ≥ 2 года |
| `has_live_evidence` | +3 | Есть live trading evidence |
| `has_3_benchmarks` | +2 | Сравнение с ≥ 3 бенчмарками |
| `has_robustness_tests` | +2 | Robustness по активам/периодам |
| `open_code_and_data` | +3 | Открытый код И данные |
| `known_author` | +2 | Автор с track record |
| `top_tier_venue` | +3 | Top-tier журнал/конференция |

### 54.4. Порог инджестинга


## ЭТАП 56. ИЗВЛЕЧЕНИЕ ИЗ НАУЧНЫХ СТАТЕЙ

### 56.1. Инструменты

Используй те же инструменты, что в ЭТАПЕ 4 (PyMuPDF, ebooklib).

Для статей добавь:

- Извлечение **ссылок** (References) через `GROBID` (если установлен) или регулярные выражения

### 56.2. Специфика извлечения из статей

В отличие от книг, статьи имеют фиксированную структуру. Извлекай секции отдельно:

```
Abstract          → один чанк, тип "abstract"
Introduction      → 1–2 чанка
Related Work      → 1 чанк (используется для графа цитирования)
Methodology       → каждый подраздел = отдельный чанк
Results           → таблица + описание = один чанк
Discussion        → 1–2 чанка
Conclusion        → один чанк
References        → НЕ инджестировать как знание.
                     Сохранять как граф цитирования.
Appendix          → отдельные чанки, если содержат формулы/доказательства
```

### 56.3. Контроль качества извлечения

Дополни ЭТАП 5. Для статей добавь:

- Проверка наличия Abstract (если нет → `NEEDS_REVIEW`)
- Проверка наличия References (если нет → `NEEDS_REVIEW`)
- Проверка извлечения таблиц (если таблицы не извлеклись → пометить)
- Проверка извлечения формул (если формулы не извлеклись → пометить)

### 57.1. Правила чанкинга для статей

НЕ режь статьи по количеству символов. Разрезай по секциям и подразделам.

```
  Контекст: "Краткое содержание всей работы"
```

## ЭТАП 59. ОЦЕНКА КАЧЕСТВА И ВОСПРОИЗВОДИМОСТИ

### 59.1. Автоматическая оценка воспроизводимости

Для каждой статьи вычисли `reproducibility_score` (0.0 – 1.0):

```python
def reproducibility_score(doc):
    score = 0.0

    # Код доступен
    if doc.get("has_code"):
        score += 0.25
        # Код верифицирован (запущен, тесты пройдены)
        if doc.get("code_verified"):
            score += 0.15

    # Данные доступны
    if doc.get("has_data"):
        score += 0.20

    # Методология описана достаточно детально
    if doc.get("methodology_detailed"):
        score += 0.15

    # Гиперпараметры раскрыты
    if doc.get("hyperparameters_disclosed"):
        score += 0.10

    # Рецензирована
    if doc.get("peer_reviewed"):
        score += 0.15

    return min(score, 1.0)
```

### 59.2. Сохранение оценки

Добавь в манифест поле `reproducibility` (см. ЭТАП 55).

### 59.3. Использование в retrieval

При ранжировании результатов поиска учитывай `reproducibility_score`:

```
Если два чанка имеют одинаковую семантическую релевантность,
предпочесть чанк из документа с более высоким
reproducibility_score.
```

## ЭТАП 60. ИНТЕГРАЦИЯ С КНИЖНЫМ КОРПУСОМ

### 60.1. Связывание статей с книжными утверждениями

При инджестинге статьи автоматически проверяй:

```
1. Поддерживает ли статья существующие claims из книжного корпуса?
   → Создай отношение SUPPORTS

2. Противоречит ли статья существующим claims?
   → Создай отношение CONTRADICTS
   → Запусти conflict resolution

3. Расширяет ли статья существующие claims?
   → Создай отношение EXTENDS или REFINES

4. Заменяет ли статья устаревшие рекомендации из книг?
   → Создай отношение SUPERSEDES
   → Обнови temporal_status старого claim
   → НЕ удаляй старый claim. Свяжи:
     historical_implementation → superseded_by → current_implementation
```

### 60.2. Правила обновления

НЕ обновляй `temporal_status` книжного claim на основании одной статьи.

Требуется минимум одно из:
- 2 независимых источника подтверждают изменение
- Явное `supersedes` с обоснованием
- Рецензированная статья в топ-журнале

### 60.3. Конфликты книга ↔ статья

При обнаружении конфликта между книгой и статьёй:

```
1. Зафиксируй конфликт в claims:
   contradicting_sources: [book_ref, paper_ref]

2. Классифицируй конфликт:
   REAL_CONTRADICTION     → прямое противоречие
   DIFFERENT_CONDITIONS   → разные условия применения
   TEMPORAL_SUPERSESSION  → статья обновляет устаревшее
   METHODOLOGICAL         → разница в методологии

3. НЕ разрешай конфликт автоматически.
   Сохрани для ручного разбора или для comparison в API.
```

## ЭТАП 64. РАСПИСАНИЕ ОБНОВЛЕНИЯ КОРПУСА

### 64.1. Ежедневно

```
1. Автоматический скрипт проверяет arXiv RSS
2. Скачивает релевантные статьи
3. Сохраняет в 02_arxiv\
4. Обновляет arxiv_seen.json
5. Записывает лог в ingestion_log.jsonl
```

### 64.2. Еженедельно (воскресенье)

```
1. Проверка Semantic Scholar по ключевым запросам
2. Проверка SSRN (вручную или скрипт)
3. Проверка индустриальных отчётов (RSS + вручную)
4. Запуск Quality Gate для всех новых документов
5. Пакетный инджестинг прошедших фильтр в основной корпус
6. Обновление графа цитирования
7. Проверка конфликтов с существующими claims
```

### 64.3. Ежемесячно

```
1. Глубокий обзор: что нового в топ-журналах
2. Обновление citation_count для ранее инджестированных статей
3. Проверка temporal_status: не устарели ли эмпирические результаты
4. Пересмотр evidence_level для спорных claims
5. Экспорт обновлённого knowledge_pack.json для приложения
```

### 64.4. Ежеквартально

```
1. Полный аудит корпуса: что инджестировано, что нет
2. Обновление списка ключевых слов для фильтрации
3. Пересмотр порогов Quality Gate
4. Очистка quarantine: ручная проверка накопленных документов
5. Обновление golden set для evaluation
```
